## 1. 결정의 구분

**사용자 확정:** 실제 출시 목표, Modular Monolith 채택, 기초부터 단계적으로 개발, 기존 작업·공개 이력 보존.

**이번 승인 제안:** PF00 검증 기반과 PF01 관계·권한 모델. 설계 검토 승인은 코드 변경, 실제 고객 데이터 수집, 외부 계정 연결, 유료 서비스 가입, IAM/branch protection 변경을 자동 승인하지 않는다.

이 문서는 이전 `production_blueprint.md`의 넓은 방향을 유지하면서 첫 두 기반 작업을 좁힌다. PF01 상세는 기존 `PF01_foundation_design.md` v0.1을 대체하는 0.2 제안이다. 이전 파일은 보존한다. 그때의 feature baseline 대신 머지된 main을 조사 기준으로 사용한다. 이후 실행 지시서를 만들 때에는 원격 HEAD를 다시 확인해 별도의 실행 TARGET_REF로 고정한다. [G01]

## 2. 첫 제품과 첫 구현을 구분한다

첫 출시 제품은 소형 임대주택의 유지관리 요청이 접수→관리자 확인→정보 보완→담당·일정→처리→완료 확인·재접수까지 끝나는 서비스다. 월세 수납, 회계, 중개, 전자계약, 범용 채팅, 업체 자동배정, IoT, 예측정비는 첫 출시 필수 범위가 아니다.

첫 구현(PF02-A~E)은 더 작다. **인증된 관리자→조직→건물·호실→세입자 초대·연결→자기 호실 텍스트 신고→담당 관리자 확인·답변→입주 연결 종료→이전 세션의 접근 차단**을 실제 PostgreSQL/API/Web/Mobile 경로에서 검증한다. 합성 데이터로 먼저 실행하지만 임시 로그인·가짜 영속성을 출시 구현인 것처럼 대체하지 않는다.

초기 실제 데이터 사용은 비공개 초대형 파일럿으로 제한하는 것을 제안한다. 관리조직의 활성화는 별도 확인을 거치며, 가입·주소 검색 성공을 소유권 증명으로 표시하지 않는다. 같은 공공주소가 발견돼도 다른 조직의 건물/사람/티켓을 자동 합치지 않는다.

## 4. 기존 FROZEN과 새 기능의 관계

과거 FROZEN 커밋·인수 기록·테스트 의미는 그대로 보존한다. 그러나 신규 production 요구는 과거 데모의 결함만으로 설명할 수 없다. 따라서 **역사적 기준선 보존**과 **승인된 신규 변경**을 분리한다.

PF00에서 테스트 설정을 바꾸는 경우 원인·대상·검증 범위를 좁혀 승인한다. PF02에서는 새 API/관계 모델 도입을 위한 명시적 변경 명세가 과거 demo 한정 조건을 해당 범위에서만 대체한다. 이 패키지 자체가 frozen code의 광범위 수정 허가는 아니다. 실행 계획에는 정확한 경로·대체할 계약·보존할 회귀·배포 범위를 제시한다. [G07–G08]

기존 domain의 Safety/Protocol/Routing 규칙은 재사용 우선이다. 승인되지 않은 책임 판정·안전 인증·위험한 자가 수리 안내를 추가하지 않는다. 로그인/실호실을 넣기 위해 application과 DTO를 진화시키는 것은 허용 요청 대상이지, 단순 DB adapter 교체라고 축소하지 않는다. [G06]

## 5. Modular Monolith 운용안

Next Web와 서버 API, Expo Mobile, 공통 public 계약, 업무별 application/domain의 단일 백엔드 코드베이스를 유지한다. 파일·인증·메일 등의 공급자는 adapter 경계 밖으로 분리한다. 처음부터 별도 API 서비스, Kubernetes, Kafka, Redis, CQRS/event-sourcing 전체를 도입하지 않는다.

업무별 데이터 소유권은 Identity/Access, Property/Occupancy, Maintenance, Evidence, Messaging/Delivery로 구분한다. 모듈을 나눈다고 DB 접근권한이 자동 분리되지는 않는다. 타 모듈의 쓰기는 공개 application operation을 통해 수행하고, 내부 테이블 직접 갱신은 허용하지 않는 의존성 검사를 후속 plan에 포함한다.

PostgreSQL은 제안된 production 저장소이며 호스팅 업체는 미선정이다. worker는 같은 코드베이스·스키마 계약에서 별도 프로세스로 실행할 수 있다. outbox가 필요한 때 추가하되 대기 레코드/중복 방지 키 설계는 지금부터 예약한다. [S10]

| 결정 | 제안 기본값 | 이유/범위 |

| 실거주 | 호실의 입주기간과 입주자 연결을 분리 | 공동거주와 구성원만의 퇴거를 표현 |
| 주민 티켓 | 유효한 입주자도 본인 신고만 열람 | 같은 호실 거주가 타인의 대화 열람 동의는 아님 |
| 퇴거 | 현재 입주 접근 종료, 계정/다른 관계는 보존 | 새 입주자에게 과거 개인자료를 넘기지 않음 |
| 과거 이력 | 초기 resident API에는 과거 입주 내역 자체를 제공하지 않음 | 익명성 검증 전 자동 공유 금지 |
| 인증 | 검증된 인증 제품의 표준 flow, 자체 비밀번호 체계 없음 | provider 선정은 별도 절차 |
| demo | 운영에서 legacy v1·reset·fixture fallback 차단 | 단순 UI 숨김으로 대체 불가 |
| 첫 입력 | 텍스트 신고/답변부터, 사진·AI 후속 | 관계·접근·저장 동작부터 검증 |

## 7. 위험과 출시 차단 조건

| 영역 | 지금 상태 | 파일럿/출시 전 필요한 증거 |
|---|---|---|
| cold-cache | 실행자 보고로 재현됨; 이번 미실행 | PF00 진단과 fresh run |
| 사용자/권한 | 상세 설계 제안 | F01~F44 DB/API/UI 시험 |
| 인증/운영 DB | 공급자 미선정 | 비용·리전·권한·복원·표준 flow 검토 |
| 개인정보 | 데이터 분류만 제안, 법률 검토 완료 아님 | 목적·보유·위탁/국외이전·삭제·백업 정책, 실제 절차 |
| 안전 | 기존 demo hard-stop만으로 출시 안전성 입증 불가 | 한국 상황별 검토된 안내·사람에게 연결되는 절차 |
| 사진/알림 | 후속 범위 | 비공개 파일 권한과 전달 실패/재시도 검증 |
| 앱 설치/호환 | export가 실기기 증거는 아님 | 서명된 앱, 실제 iOS/Android, 업데이트·구버전 호환 |
| 사업 운영 | 인력/응대시간/비용 불명 | 운영 책임자·지원시간·장애대응·월 예산 |

공개는 테스트 수나 완료율로 판단하지 않는다. Launch Gate는 기능 흐름, 권한/보안, 설치·백업·복원, 알림/운영, 개인정보/안전, 실제 기기, 승인된 파일럿 평가, 비용·책임자까지 각각 증거가 있어야 한다. 실제 지원 인력을 모르는 상태에서 24시간 감시·즉시 출동·응답 SLA를 약속하지 않는다.

## 8. 승인 범위와 바로 다음 작업

이 기획의 승인 대상은 PF00의 진단·검증 범위와 PF01의 관계·권한 기본 정책이다. 첫 실행 지시서는 **PF00-A/B**만 대상으로 작성한다. PF02까지 한 번에 승인받거나 구현하지 않는다.

공급자/요금·리전, 실제 관리 권한의 확인 방식, 데이터 보유·삭제 정책은 `DECISION_REQUIRED`로 남긴다. 이 결정이 없어도 PF00 및 PF01 검토는 가능하지만 실제 인증 연결 및 실데이터 파일럿으로 넘어갈 수는 없다.
