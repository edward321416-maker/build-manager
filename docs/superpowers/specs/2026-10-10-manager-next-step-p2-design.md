- 날짜: 2026-10-10. 작성: Claude Opus 5.5 (Claude Code).
- 위험 등급: 일반. 화면 배치와 문구만 바꾸고 API, DB, 권한은 그대로다.
- 근거: [기능 배치·메뉴 점검](../../../research/ux/2026-10-10-menu-audit.md)의 F-04, F-05, F-06, F-20과 CLM-101–CLM-103
- 결정

  - 같은 날 이 설계안("이대로 진행")을 승인했다.

## 문제

[점검 4–5절](../../../research/ux/2026-10-10-menu-audit.md#5-문제-목록)에서 확인한 문제다.

- 관리자 할 일이 상세 아래쪽(휴대폰에서 1,400–5,100px)의 접힌 칸에 흩어져 있다. 처리 방법 결정, 업체 연결, 처리 기록, 업체 보고 확인, 정비 사실이 모두 그렇다.
- 업체 칸은 처리 방법이 정해지기 전에는 이유 없이 비어 있다. 결정한 뒤에도 요청을 다시 열어야 갱신된다.
- 업무함 행에는 제출 전이나 결정 필요 같은 신호가 없다.
- 상단 `업무 정보` 버튼을 누르면 칸 제목만 화면 맨 아래에 걸리고 내용은 보이지 않는다.

## 범위

1. 관리자 접수 상세에서 요약 바로 아래에 `다음 할 일` 구역을 둔다. 안내 한 줄, 설명 한 줄, 필요할 때 버튼 하나로 이루어진다.
   - 버튼을 누르면 해당 컨트롤이 들어 있는 접힌 칸(`추가 확인·결정 기록` 또는 `업무 정보`)을 열고, 그 칸을 화면 위로 올린 뒤 포커스를 준다.
   - 상태별 안내는 아래 표를 따르고, 판단은 `apps/web/src/app/core/manager-next-step.ts`의 순수 함수가 한다.
   - 할 일이 없으면 구역을 그리지 않는다(완료 뒤 정비 사실까지 남긴 경우). 아직 알 수 없을 때도 그리지 않는다(업체 정보를 불러오는 중).
2. 업무함 행
   - 화면이 이미 받아 둔 접수 목록(접수 상태와 진행 기록 포함)을 접수 번호로 이어 붙인다. 그래서 서버를 바꾸지 않는다.
   - 제출 전 요청은 `접수` 대신 `제출 전`이다(P1과 같은 이름).
   - `추가 확인 필요`와 `긴급 확인 필요`는 접수 상태 이름 그대로 상태 표시로 붙인다.
   - 결정이 필요한 요청에는 `처리 방법 결정 필요`를 보조 글자로 적는다.
   - 접수 목록 API는 최근 접수 100건만 돌려준다. 그보다 오래된 행에는 표시를 붙이지 않고, 지금처럼 업무 상태만 보인다.
   - 요청을 열 때는 그 요청과 접수 목록을 함께 다시 읽는다. 업무함도 요청을 고를 때마다 행을 다시 읽으므로, 행 표시와 업무 상태가 같은 시점의 것이 된다.
   - 처리 기록이나 결정 뒤에 다시 읽은 요청도 목록에 반영한다.
3. 업체 칸
   - 처리 방법이 업체 경로가 아니고 연결된 업체도 없으면 선행 조건을 적는다: "업체에 보내려면 먼저 처리 방법을 '일반 수리업체'나 '제조사 A/S'로 정해 주세요."
   - 안전 확인이 필요한 접수에는 이 줄을 적지 않는다. 결정 화면이 처리 방법 선택을 주지 않기 때문이다.
   - 결정 화면이 결정을 저장할 때마다 요약, 업체 칸, 업무함 행을 바로 다시 읽는다. 상태가 그대로인 경로 수정(직접 지정을 다시 한 경우)도 포함한다. 지금은 요청을 다시 열어야 바뀐다.
4. `/core` 안에 끼워 넣은 결정 화면(옛 컴포넌트)은 두 번째 `main` 영역과 자체 뒤로 가기 링크를 만들지 않는다. P1의 질문 화면과 같은 방식이다.
5. 상단 `업무 정보` 버튼은 칸을 펼친 뒤 칸 전체를 화면 위로 올린다(F-20).

- 버튼은 보조 버튼 모양이다. 처리 기록 칸에 이미 채운 파랑 버튼이 있어서, 화면당 하나 규칙(8.1)을 지킨다.
- 업체 단계는 업체 기능이 켜진 모드(B1)에서만 나온다. 그 밖의 모드에서는 업체 경로도 직접 처리 안내로 간다.

## 접근성

- 구역 이름과 제목은 모두 `다음 할 일`이다. 대화의 `지금 할 일`, 세입자의 `지금 할 일: 추가 확인`과 구분된다.
- 포커스는 화면 읽기가 이름을 읽을 수 있는 곳에 놓는다.
  - 결정 칸은 칸 제목(`추가 확인·결정 기록`)에 놓는다.
  - 업체 칸과 정비 사실 칸은 칸 자체에 놓는다(`tabIndex=-1`). 칸 이름은 `업체 연결 및 작업 요청`, `호실 정비 사실 기록`이다.
  - 처리 기록은 입력칸(`처리 기록`)에 놓는다. 이름 없는 양식 대신, 바로 쓸 수 있는 곳이다.
- 업무함 행의 새 표시는 글자와 색을 함께 쓴다(2.3).

- 화면 흐름
  - core(업체 기능 꺼짐): 390×844에서 다음을 확인한다.
    - 행에 `제출 전`과 `처리 방법 결정 필요`가 보인다.

    - `업무 정보` 버튼을 누르면 칸 내용이 화면 위쪽 절반 안에 들어온다.
    - 결정 칸을 열어도 `main` 영역은 하나이고 `← 접수 목록` 링크가 없다.
  - core, 1440×900: 업무함 행이 요청 옆에 보이는 폭이다.
    - 결정하면 행에서 `처리 방법 결정 필요`가 사라진다.

    - 결정 전 업체 칸에 선행 조건이 보인다.
    - 직접 처리 경로로 정하면 안내가 `처리를 시작하면 기록해 주세요.`이고, 선행 조건이 남는다.
    - 그 경로를 `일반 수리업체`로 고치면 안내가 `업체에 작업을 보내 주세요.`로 바뀌고, 버튼이 업체 칸으로 이동한다.
    - 업체 칸은 다시 열지 않아도 준비 입력칸을 보여 준다.
- 업체 보고 도착 같은 뒤 단계는 단위 테스트로 확인한다. 화면에서는 디자인 점검과 합성 데이터 걷기로 본다.

## 위험과 되돌리기

- 결정 화면과 질문 화면은 상태를 알릴 때마다 요약을 다시 읽는다. 같은 상태이면 다시 읽지 않고, 가장 최근 읽기만 반영한다(P1과 같은 경로).
- 결정 화면은 결정을 저장할 때마다 한 번 더 다시 읽게 한다. 같은 상태로 경로만 고치는 경우가 있기 때문이다. 그때 알린 상태는 읽은 것으로 쳐서 두 번 읽지 않는다.
- 늦게 도착한 읽기는, 사용자가 이미 다른 요청으로 옮겼으면 화면을 바꾸지 않는다.
- 요청을 열 때 접수 목록도 다시 읽으므로, 요청 하나를 열 때마다 요청이 하나 더 나간다.
- 업체 정보를 불러오는 동안 구역을 그리지 않으므로 잠깐 늦게 나타날 수 있다.
- 되돌리기: 이 PR을 되돌리면 된다. 서버, DB, API 계약은 바꾸지 않는다.
