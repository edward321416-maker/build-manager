## 설계

`scripts/demo-smoke.mjs`만 바꾼다. 매시간 점검(`demo-health.yml`)은 `--http-only`라서 영향이 없다.

1. 저장 단계(지금 있는 `write check saves a synthetic request before submission`)는 그대로 두고, 접수 응답(201)에서 그 접수의 `ticketId`를 읽어 둔다.
2. 저장이 성공해 번호가 있을 때만 새 단계 `write check closes its synthetic request`를 돈다.
   - 관리자로 들어가(1280px, `관리자로 체험하기`) 페이지 안에서 앱과 같은 요청을 보낸다.
     - `GET /api/v2/core/access`로 조직 id와 CSRF 값을 받는다.
     - `POST /api/v2/core/tickets/{id}/handling`으로 `처리 시작`(`IN_PROGRESS`)과 `처리 완료`(`COMPLETED`)를 차례로 기록한다. 앞의 것이 200이 아니면 뒤의 것은 보내지 않는다.
     - 머리글은 화면과 같다: `x-core-organization`, `x-b1-csrf`, JSON.
   - 세입자로 들어가(390px, `세입자로 체험하기`) `POST /api/v2/core/tickets/{id}/outcome/resolved`로 '해결됐어요'를 확인하고, `GET /api/v2/core/tickets/{id}`로 작업 상태를 다시 읽는다.
   - 통과 조건: 처리 시작 200, 처리 완료 200, 해결 확인 200 또는 201, 다시 읽은 작업 상태 `COMPLETED`
   - 실패하면 `FAIL` 줄에 접수 번호 앞 여섯 자리와 각 응답 코드를 적는다. 운영자가 그 접수를 손으로 닫을 수 있게 하려는 것이다. 주소는 지금처럼 가린다.
   - 각 단계가 끝나면 지금처럼 그 페이지의 로그아웃 폼으로 세션을 닫는다.
3. 페이지 안에서 도는 두 함수(관리자 닫기, 세입자 확인)는 내보내서(export) 가짜 `fetch`로 시험한다. 페이지에서는 기본값인 페이지의 `fetch`를 쓴다.
4. 처리 메시지는 안전 판정 단어를 피한다: `배포 점검용 합성 요청이라 정리해요.`, `배포 점검용 합성 요청 정리를 마쳤어요.`
5. `deploy/vm/README.md`의 `--write-check` 줄을 "저장한 뒤 스스로 닫는다"로 고친다.

### 바꾸지 않는 것

- 서버·API·DB·화면 코드, 매시간 점검, 다른 점검 항목
- 이미 데모에 있는 접수(이 실행이 만든 번호만 다룬다)

## 위협·남용 사례

| ID | 누가 어떻게 | 막는 방법 | 시험 |
| --- | --- | --- | --- |
| T1 | 스크립트가 진짜 사용자의 요청을 닫는다 | 이 실행이 방금 받은 201 응답의 `ticketId`만 쓴다. 번호를 밖에서 넘기는 옵션은 없다 | 닫기 함수는 받은 번호의 경로로만 요청한다(번호를 URL 인코딩) |
| T2 | 닫기가 중간에 멈춰 접수가 `처리 중`으로 남는다 | 실패 줄에 번호와 응답 코드를 남기고, 실행은 실패(종료 코드 1)로 끝난다. 다음 실행은 그 접수를 건드리지 않는다 | 처리 시작이 실패하면 처리 완료를 보내지 않는다 |
| T3 | 주소, CSRF 값, 세션이 출력에 샌다 | 페이지 함수는 응답 코드와 작업 상태만 돌려준다. 출력은 지금처럼 가린다 | 함수의 반환값에 CSRF 값이 없다 |
| T4 | 처리 메시지가 안전 판정에 걸린다 | 메시지를 정해 두고 판정 함수로 시험한다 | `evaluateSafety`가 두 메시지를 올리지 않는다 |
| T5 | 다른 출처에서 이 요청을 흉내 낸다 | 데모 페이지 안에서 같은 출처로만 보낸다. 서버의 Origin·CSRF 검사는 그대로다 | 머리글 시험(조직 id, CSRF) |

## 시험 (`tests/architecture/demo-smoke.test.ts`)

1. 관리자 닫기: 가짜 `fetch`가 받은 요청이 차례로 `GET access`, `POST …/handling IN_PROGRESS`, `POST …/handling COMPLETED`이고, 머리글에 조직 id와 CSRF 값이 있으며, 함수가 두 응답 코드를 돌려준다.
2. 관리자 닫기: 처리 시작이 409면 처리 완료를 보내지 않고 그 코드를 돌려준다.
3. 세입자 확인: `POST …/outcome/resolved`(받은 `clientRequestId`)와 `GET …/tickets/{id}`를 보내고, 해결 확인 코드와 작업 상태를 돌려준다. CSRF 값은 돌려주지 않는다.
4. 번호에 `/`나 `?`가 섞여도 경로가 인코딩된다.
5. 두 처리 메시지가 안전 판정에 걸리지 않는다.

- 새 함수라서 첫 실패는 "함수 없음"이다(구조적 실패). 그래서 행동 증거로, 처리 시작이 실패해도 완료를 보내는 변형 등을 만들어 시험이 잡는지 돌려 본다(변형 시험).
- 브라우저 부분은 단위 시험이 없다. 병합 뒤 운영자 확인을 받고 데모에서 `--write-check`를 한 번 돌려, 접수가 저장된 뒤 닫히고 세입자 알림이 다시 0건인지 확인한다.

## 남은 위험

- 데모의 화면이나 API가 바뀌면 이 단계가 먼저 깨질 수 있다. 그때는 실패 줄로 알 수 있다.
- 쓰기 확인을 돌릴 때마다 닫힌 시험용 접수가 하나씩 기록으로 남는다(끝난 요청 목록에는 보인다). 지우지는 않는다.
