# 세입자 접수 마무리 (P1) 설계

- 날짜: 2026-10-10. 작성: Claude Opus 5.5 (Claude Code). 위험 등급: 일반(화면 배치와 상태 문구. 질문 내용, 안전 판정, 필수 증빙 규칙은 바꾸지 않음).
- 근거: [기능 배치·메뉴 점검](../../../research/ux/2026-10-10-menu-audit.md)의 F-02(심각도 4)와 F-10 일부, CLM-099·CLM-100.
- 결정:
  - 운영자가 2026-10-10에 "흐름 결함부터"를 골랐다(CLM-112).
  - 같은 날 이 설계안("이대로 진행")을 승인했다. 승인한 안은 다섯 가지다.
    1. 질문을 요약 바로 아래에 펼친다.
    2. 첫 질문을 바로 보이게 한다.
    3. 상태 문구를 역할별로 쓴다.
    4. 제출하면 요약을 갱신한다.
    5. 세입자 목록 행에 `제출 전`을 표시한다.

## 문제

[점검 4–5절](../../../research/ux/2026-10-10-menu-audit.md#4-과업-걷기-결과)에서 확인한 문제다.

- `접수하기`를 눌러도 요청은 `작성 중`에 머문다. 안전 질문 4개를 포함한 필수 단계는 맨 아래 접힌 `추가 확인` 안에 있다(390px에서 약 1,400px 아래).
- 세입자 목록과 관리자 목록에는 같은 요청이 `접수`로만 보여서, 아직 제출하지 않았다는 사실이 드러나지 않는다.

## 범위

포함:

1. 세입자 접수 상세에서 다음 세 상태일 때는 질문을 요약 바로 아래 `지금 할 일`(TaskZone)에 펼쳐 둔다. 이때 맨 아래 접힌 `추가 확인`은 그리지 않는다.
   - 처리 상태 `OPEN`이면서 접수 상태가 `IN_PROGRESS`(제출 전)
   - 처리 상태 `OPEN`이면서 접수 상태가 `NEEDS_MORE_INFO`(관리자가 추가 확인을 요청함)
   - 처리 상태 `OPEN`이면서 접수 상태가 `SAFETY_ESCALATED`(안전 확인 필요). 안전 안내가 접힌 칸에 숨지 않게 한다.
   - 관리자가 세입자 답변을 기다리는 질문을 보냈다면, 대화의 `지금 할 일`(답변 보내기)을 먼저 두고 질문 구역을 그다음에 둔다. 사진과 진행 이력보다는 위다. 기존 규칙(답변 버튼이 390×844 첫 화면 안, `core-login-e2e/spatial.spec.ts`)을 지키기 위해서다. 관리자 질문이 없으면 질문 구역이 요약 바로 아래에 온다.
2. 그 밖의 상태에서는 지금처럼 맨 아래 접힌 `추가 확인`에 기록으로 남긴다.
3. 제출 전 요청의 상태 표시
   - `접수` + `접수 상태: 작성 중` 두 칸 대신 `제출 전` 한 칸을 보여 준다.
   - 세입자와 관리자에게 같은 이름을 쓴다(디자인 규칙 8.7). 색은 `대기·확인 필요` 짝이다(2.3).
   - 역할별 설명 한 줄은 아래 문구 표를 따른다.
4. 질문 화면에서 접수 상태가 바뀌면(제출, 안전 확인으로 전환) 요약이 서버의 최신 접수를 다시 읽는다. 지금은 다시 열어야 바뀐다.
   - 맨 아래 기록의 질문 화면에도 적용한다. 관리자가 먼저 처리를 시작한 요청이 여기에 해당한다.
   - 가장 최근 읽기만 반영한다.
   - 질문 구역이 사라지면 포커스를 접수 제목으로 옮긴다. 다시 읽은 상태가 제출된 상태(`PARTIAL`·`READY_FOR_REVIEW`)일 때만 "수리 요청을 관리자에게 보냈어요."를 알린다. 관리자가 처리를 시작해 구역이 닫힌 경우처럼 다른 이유로 닫혔으면 알리지 않는다.
   - 질문 화면은 보이는 상태로 키를 정한다. 사진을 올릴 때마다 다시 그려지지 않게 하기 위해서다.
4-1. 추가 확인 라운드
   - 세입자가 답할 때마다 서버 상태는 `IN_PROGRESS`로 돌아간다.
   - 진행 기록에 `FINALIZED`(수리 요청 제출)가 있으면 이미 한 번 보낸 요청이다. 그래서 `제출 전`이 아니라 `추가 확인 필요`로 보이고 문구도 추가 확인 문구를 쓴다.
5. 세입자 `최근 접수` 행에서 제출 전 요청을 `제출 전`으로 표시한다.
6. `/core` 안에 끼워 넣은 질문 화면에서 다음 셋을 빼고, 질문과 `상태 새로고침`만 남긴다.
   - 두 번째 `main` 영역
   - 자체 `← 접수 목록` 링크(화면에 이미 `← 목록으로`가 있음)
   - 옛 `접수 상태` 블록(`상태: 작성 중`, `정보 상태: 필수 정보 부족`). 위쪽 요약의 `제출 전`과 어긋나서 같은 상태가 두 이름으로 보였다.

## 문구

요약의 설명 한 줄:

| 상황 | 세입자 | 관리자 |
| --- | --- | --- |
| 상태 칸(제출 전) | 제출 전 | 제출 전 |
| 제출 전 | 아직 보내지 않았어요. 아래 질문에 답하고 '수리 요청 제출'을 눌러야 관리자에게 전달돼요. | 세입자가 아직 질문에 답하는 중이에요. |
| 추가 확인 요청 | 관리자가 추가 확인을 요청했어요. 아래 질문에 답해 주세요. | 세입자의 추가 답변을 기다리고 있어요. |
| 안전 확인 필요 | 안전 확인이 필요해요. | 안전 확인이 필요한 접수예요. |
| 제출 뒤(정보 부족) | 관리자에게 보냈어요. 부족한 정보가 있으면 관리자가 다시 물어볼 거예요. | 세입자가 제출했어요. 필수 정보가 부족해요. |
| 처리 방법 결정 뒤(APPROVED·OVERRIDDEN) | 관리자가 확인했어요. 처리를 기다리고 있어요. | 처리 방법을 정했어요. |
| 제출 뒤(그 밖) | 관리자에게 보냈어요. 확인을 기다리고 있어요. | 세입자가 제출했어요. |
| 처리 중 | 관리자가 확인하고 있어요. | 처리 중이에요. |
| 처리 완료 | 관리자가 완료로 기록했습니다.(바꾸지 않음, P3) | 같음 |

세입자 `지금 할 일` 구역의 안내 한 줄과 알림:

| 상황 | 문구 |
| --- | --- |
| 제출 전 | 질문에 모두 답하면 '수리 요청 제출' 버튼이 나와요. |
| 추가 확인 요청 | 답한 뒤 다시 제출해 주세요. |
| 안전 확인 필요 | 아래 안내를 먼저 확인해 주세요. |
| `접수하기` 직후 알림 | 접수 내용을 저장했어요. 이어서 아래 질문에 답해 주세요. |
| 질문 구역에서 제출한 뒤 알림 | 수리 요청을 관리자에게 보냈어요. |

## 접근성

- 질문 구역은 `지금 할 일` 제목을 보이고, 영역 이름은 `지금 할 일: 추가 확인`이다. 대화의 `지금 할 일` 구역과 이름이 겹치지 않는다.
- 접수 직후 포커스는 지금처럼 접수 제목에 둔다. 390×844에서 첫 질문이 스크롤 없이 보이는지 테스트로 확인한다.
- 상태는 글자와 색을 함께 쓴다(2.3).

## 테스트

- 단위
  - `TicketProgress`: 제출 전이면 `제출 전` 한 칸이고 `접수 상태:` 줄이 없다. 그 밖의 상태는 지금과 같다.
  - `DraftBadge`의 글자와 상태 속성
- 화면 흐름(core e2e)
  - 기존 기대값을 바꾼다. 접수 직후 `work-status`는 `제출 전`이다. 저장 알림 문구가 바뀐다. 질문을 열 때 `추가 확인` 펼치기가 필요 없다.
  - 새 확인
    - 390×844에서 `접수하기` 뒤 `지금 할 일: 추가 확인` 영역과 첫 질문이 첫 화면 안에 보인다.
    - 제출하면 요약이 다시 읽혀 `제출 전`이 사라지고, 알림과 포커스가 접수 제목으로 온다.
    - 세입자 목록 행과 관리자 상세에 `제출 전`이 보인다.
    - 추가 확인 라운드에서는 답한 뒤에도 `제출 전`이 되지 않고, `다시 제출하기`로 끝난다.
- 디자인 점검
  - `scripts/design-audit.mjs` 발견 0건, 390·1280 캡처
  - 이 스크립트는 접수 저장 알림 글자로 접수 완료를 확인하므로, 그 글자를 새 문구로 바꾼다.

## 위험과 되돌리기

- 질문 구역이 위로 오면서 대화의 `지금 할 일`과 함께 두 구역이 보일 수 있다. 영역 이름이 달라 화면 읽기에서도 구분된다.
- 질문 화면의 상태 알림 때문에 요약을 다시 읽는다. 같은 상태면 다시 읽지 않아 반복 요청이 없다.
- 되돌리기: 이 PR을 되돌리면 된다. 서버, DB, API 계약은 바꾸지 않는다.
