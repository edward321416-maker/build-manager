# 올린 사진을 필수 증빙으로 지정 (P1b) 설계

- 날짜: 2026-10-11. 작성: Claude Opus 5.5 (Claude Code).
- 위험 등급: 고위험. 필수 증빙 판정과 추천 경로라는 판단 기준에 닿고, DB 마이그레이션을 더한다(DEV-01, DEV-08).
- 근거
  - [메뉴 점검](../../../research/ux/2026-10-10-menu-audit.md) F-03(심각도 3)과 P1b 항목.
    - 세입자가 질문에 모두 답하고 제출해도 결과가 늘 "정보 부족 · 필수 정보 부족"이다.
    - 세입자가 할 다음 행동이 없고, 관리자 쪽에도 추천 경로가 없다.
  - 운영자 결정 2026-10-11: "올린 사진을 증빙으로 지정 (추천)". 검토한 다른 안은 "/core에서는 증빙 요구 빼기"와 "관리자가 사진 보고 확인"이다.
- 결정: 운영자가 2026-10-11에 이 스펙을 승인했다("승인 (추천)"). 자세한 내용은 아래 "결정" 절에 있다.

## 원인 (코드로 확인함)

1. `/core` 흐름에는 증빙을 넣는 경로가 없다.
   - Core API(`apps/web/src/server/core-flow/http.ts`)가 받는 접수 동작은 생성, 답변, 제출, 처리, 사진뿐이다.
   - 관리자가 추가 확인 요청에 증빙 유형을 넣으면 `INVALID_INPUT`으로 막는다.
   - 질문 화면(`ticket-intake.tsx`)도 `/core`에서는 증빙 단계를 건너뛰고 "참고 사진은 필수 증빙 판정과 별개"라고만 보여 준다.
2. 기존 증빙 유스케이스(`submitTicketEvidence`)는 예전 데모용 합성 픽스처(`DEMO_FIXTURE`)만 만든다. 도메인은 세입자 업로드(`TENANT_UPLOAD` + `storageRef`)를 받을 수 있지만, 그것을 만드는 기능은 없다.
3. Core 사진은 `core_flow.ticket_photo`에 "참고 첨부"로만 저장된다. 사진 선택 화면도 "자동 분석이나 필수 증빙 판정에 사용하지 않습니다"라고 안내한다. 처음 설계 때 일부러 정한 분리다.
4. 결과
   - 누수의 "누수 부위 사진"(`LEAK_AREA_PHOTO`)과 난방의 "보일러 표시창 사진"(`CONTROL_PANEL_PHOTO`)은 늘 비어 있다.
   - 그래서 판정(`evaluateEvidence`)이 `MISSING_REQUIRED`가 되고, 제출 상태가 `PARTIAL`이 된다.
   - 관리자 쪽에는 "필수 정보가 아직 부족해 추천 경로가 없습니다"가 나와, 매번 경로를 직접 지정해야 한다.

## 목표

- `/core`에서 세입자가 필수 증빙마다 사진을 하나씩 고를 수 있다. 이미 올린 사진에서 고르거나 그 자리에서 새로 올린다.
- 필수 질문과 필수 증빙이 모두 채워지면 제출 상태가 `READY_FOR_REVIEW`(검토 대기)가 되고, 관리자 검토 화면에 추천 경로가 나온다.
- 판정 규칙(`evaluateEvidence`)과 안전 판정은 바꾸지 않는다. 안전 신호는 지금처럼 다른 모든 상태보다 앞선다.
- 사진을 자동으로 분석하지 않는다. 어떤 사진을 고를지는 세입자가 정하고, 사진이 맞는지는 관리자가 본다.

## 범위

PR 두 개로 나눈다(DEV-02: 합쳐 1000줄을 넘을 것으로 보임).

### PR 1: 서버

1. API: `POST /api/v2/core/tickets/{id}/evidence`
   - 본문: `{ "evidenceType": "LEAK_LOCATION" | "BOILER_DISPLAY" | "FIXTURE_VIEW" | "GENERAL_VIEW", "photoId": "<uuid>" }`. 유형 이름은 지금 공개 계약의 이름을 그대로 쓴다.
   - 세입자만 부를 수 있다.
2. 서버가 기록하기 전에 확인하는 것. 하나라도 어긋나면 기록하지 않는다.
   - 세입자 세션이고, 이 접수를 볼 수 있다(기존 `read_ticket`·RLS).
   - 사진이 이 접수에 올린 사진이다. 같은 조직의 `core_flow.list_photos`로 확인하고, 사진은 지울 수 없으므로 확인한 뒤 바뀌지 않는다.
   - 증빙 유형이 지금 프로토콜에서 켜져 있는 요구 항목이다. 예를 들어 누수 위치가 기기가 아니면 `FIXTURE_VIEW`는 받지 않는다.
     - 켜져 있는지는 도메인 함수 `activeEvidenceRequirements`가 판정과 같은 방식(질문마다 첫 답변, 빈 답변 제외)으로 읽는다.
     - 화면에 보이는 요구 목록(`evidenceRequirements`)도 같은 함수를 쓴다. 그래서 화면에 보인 유형을 서버가 거부하는 일이 없다(독립 리뷰 반영).
   - 사진 ID는 UUID 형식이다. 아니면 `NOT_FOUND`로 거부한다. 유스케이스를 다른 곳에서 불러도 사진 참조 말고 다른 값은 저장되지 않는다.
   - 접수가 아직 입력을 받는 상태다. 답변과 같은 조건이고, 완료된 처리는 바꾸지 않는다.
3. 기록 방법
   - 도메인 `Ticket.evidence`에 `{ source: "TENANT_UPLOAD", storageRef: "core-photo:<photoId>", type }`를 넣는다. `storageRef`는 서버가 확인한 사진 ID로 만들고, 브라우저가 보낸 값을 그대로 쓰지 않는다.
   - 유형마다 사진은 하나다. 같은 유형을 다시 고르면 바꾼다. 같은 사진을 두 유형에 써도 된다.
   - 같은 요청이 다시 오면 아무것도 바꾸지 않는다.
4. 이벤트: 새 종류 `EVIDENCE`를 둔다. 이력에는 "증빙 사진 지정"으로 보인다.
   - 마이그레이션 `0024_core_flow_photo_evidence.sql`이 `core_flow.store_ticket`이 받는 종류에 `EVIDENCE`를 더한다. 세입자만 쓸 수 있는 종류로 둔다.
   - 같은 마이그레이션이 `core_flow.ticket_event.kind` 제약에도 `EVIDENCE`를 더한다.
   - 기존 값을 넓히기만 한다. 그래서 예전 이미지로 롤백해도 그 코드는 계속 동작한다.
5. 세입자 상태 응답: 제출된 증빙 항목에 선택 필드 `photoId`를 더해, 어떤 사진을 골랐는지 화면이 알 수 있게 한다.
6. 범위 밖: 관리자가 추가 확인 요청에서 특정 증빙 사진을 요구하는 일. 지금처럼 막아 두고 후속 작업으로 남긴다.

### PR 2: 화면

1. 세입자(`/core`, "지금 할 일: 추가 확인")
   - 질문을 마치면, 남은 필수 증빙마다 한 화면씩 보여 준다(세입자 화면은 한 번에 한 가지 일).
     - 제목: 요구 항목 이름으로 쓴다. 예: "누수 부위가 보이는 사진을 골라 주세요".
     - 안내: 프로토콜의 촬영 안내를 그대로 쓴다. 예: "안전한 거리에서 누수 부위와 주변 위치가 함께 보이도록 촬영해 주세요."
       - 지금 요구 항목 응답에는 이 안내가 없다. 그래서 PR 2에서 요구 항목 계약에 선택 필드 `instruction`을 더하고, 서버가 프로토콜 문구로 채운다.
       - 요구 항목의 `label`은 예전 데모용 이름("DEMO 누수 위치 이미지")이라 `/core`에서는 쓰지 않는다. `/core`는 유형별 이름(예: "누수 부위 사진")을 한곳에 두고 세입자·관리자 화면이 같이 쓴다.
     - 선택: 올린 사진을 선택 타일로 보여 준다. 썸네일은 4:3이고 라디오로 고른다(디자인 규칙 8.3·8.12).
     - 주요 버튼: "이 사진으로 정하기".
   - 올린 사진이 없거나 맞는 사진이 없으면 보조 버튼 "사진 추가하기"로 그 자리에서 올린다. 접수당 3장 제한은 그대로다.
   - 필수 증빙을 다 고르면 기존 제출 단계("수리 요청 제출")로 넘어간다.
   - 글자 버튼 "사진 없이 제출하기"로 사진 없이 제출할 수 있다(D6).
   - 문구
     - 사진 선택 도움말 "사진은 참고 첨부이며 자동 분석이나 필수 증빙 판정에 사용하지 않습니다."를 "사진을 자동으로 분석하지 않아요. 접수에 꼭 필요한 사진은 다음 단계에서 직접 골라요."로 바꾼다.
     - "위 참고 사진은 필수 증빙 판정과 별개입니다…" 안내는 없앤다.
2. 관리자: 사진 목록에서 세입자가 증빙으로 고른 사진 아래에 이름을 붙인다. 예: "누수 부위 사진". 추천 경로는 기존 검토 화면에 그대로 나온다.
   - 세입자의 사진 목록에도 같은 이름을 붙여, 무엇을 골랐는지 다시 볼 수 있게 한다.
   - 관리자 상세 응답(`LandlordTicketDetailDtoSchema`)에는 아직 제출된 증빙이 없다. 그래서 PR 2에서 관리자 상세 계약과 응답에 증빙 유형과 `photoId`를 더한다(서버·계약 변경, 테스트 포함).

## 위협·남용 사례

| 사례 | 막는 방법 |
| --- | --- |
| 다른 접수나 다른 조직의 사진을 증빙으로 지정 | 서버가 사진이 이 접수에 속하는지 확인한다(같은 조직의 사진 목록, RLS). 어긋나면 기록하지 않는다. |
| `storageRef`를 꾸며 임의의 파일을 가리킴 | 브라우저는 사진 ID만 보낸다. 서버가 확인한 ID로 참조를 만든다. |
| 관리자나 업체가 세입자 대신 증빙을 지정 | 세입자 역할만 허용한다. 애플리케이션 역할 확인과 `store_ticket`의 역할 확인이 함께 막는다. |
| 요구하지 않은 유형을 붙여 판정을 흔듦 | 지금 켜진 요구 항목만 받는다. 판정 규칙은 바꾸지 않는다. |
| 제출이나 완료 뒤에 증빙을 바꿔 기록을 고침 | 답변과 같은 입력 가능 조건을 쓴다. 완료된 처리는 바꿀 수 없다. |
| 위험 상황이 사진 지정에 가려짐 | 안전 판정이 계속 먼저다. 안전 신호가 있으면 증빙과 상관없이 안전 우선으로 간다. |
| 사진을 자동 분석한다고 오해 | 문구로 자동 분석을 하지 않는다고 알리고, 실제로 분석 코드도 없다. |
| 같은 요청을 되풀이 | 같은 유형과 사진이면 바꾸지 않는다. |

개인정보: 새로 모으는 정보는 없다. 사진은 이미 저장된 것이고, 지정은 사진 ID와 유형만 남긴다. 데모에는 합성 데이터만 쓴다.

## 롤백 계획

- 코드: PR을 revert하거나 이전 이미지로 롤백한다(`deploy/vm/redeploy.sh rollback <id>`).
- 마이그레이션 0024는 허용 값을 넓히기만 한다. 예전 코드는 `EVIDENCE`를 쓰지 않으므로 그대로 동작한다. 이미 남은 `EVIDENCE` 이벤트와 `TENANT_UPLOAD` 증빙도 예전 코드에서 문제가 없다.
  - 예전 이력 화면은 모르는 종류를 대체 이름 "접수 정보 변경"으로 보여 준다(`core-screen.tsx`). PR 2에서 "증빙 사진 지정"으로 이름을 붙인다.
  - 예전 상태 응답은 증빙을 유형 이름으로만 보여 준다.
- 마이그레이션 자체를 되돌리는 일은 하지 않는다. 다음 마이그레이션으로 고친다(DEV-08).
- 배포한 뒤 문제가 생기면, 증빙 지정 API만 막는 작은 수정으로 끄고 기존 동작(늘 `PARTIAL`)으로 돌아갈 수 있다.

## 테스트 (실패부터)

- 도메인: 판정 규칙은 그대로다.
  - `TENANT_UPLOAD` 증빙은 `storageRef`가 있으면 `COMPLETE`, `fixtureRef`가 섞이거나 `storageRef`가 비면 `CONFLICTING`이다.
  - `activeEvidenceRequirements`는 질문마다 첫 답변을 읽고 빈 답변을 뺀다. 이 함수가 고른 사진을 다 내면 판정이 `COMPLETE`이고, 하나라도 빠지면 `MISSING_REQUIRED`다.
- 애플리케이션 유스케이스(새로 만듦)
  - 이 접수의 사진은 기록된다.
  - 같은 유형을 다시 고르면 바뀌고, 같은 요청은 그대로다.
  - 켜지지 않은 유형은 거부한다. 같은 질문에 두 번 답했으면 첫 답변으로 판단한다.
  - 입력이 끝난 접수는 거부한다.
  - 관리자 역할은 거부한다.
  - 안전 신호가 있으면 사진을 골라도 `SAFETY_ESCALATED`다.
  - 제출 뒤 다시 고르면 `IN_PROGRESS`로 돌아간다(답변과 같음).
  - 난방은 보일러 표시창 사진으로 `READY_FOR_REVIEW`가 된다.
  - UUID가 아닌 사진 ID는 `NOT_FOUND`다.
- 화면 응답(presenter): 같은 질문에 두 번 답해도 세입자·관리자 응답의 요구 목록이 판정과 같다.
- Core HTTP
  - 다른 접수의 사진 ID, 잘못된 형식, 모르는 유형은 거부하고 기록하지 않는다.
  - 성공하면 상태 응답에 `photoId`가 나온다.
- PostgreSQL(`tests/postgres/core-flow*.test.ts`)
  - 0024 뒤에 `EVIDENCE` 이벤트를 세입자는 쓸 수 있고 관리자는 쓸 수 없다.
  - 기존 종류는 그대로 동작한다.
- 끝에서 끝까지: 누수 접수 → 질문 답변 → 사진 지정 → 제출 → `READY_FOR_REVIEW`, 관리자 검토에 추천 경로가 나온다. 사진을 고르지 않으면 지금처럼 `PARTIAL`이다.
- 화면(PR 2): 디자인 규칙 15절 체크리스트, `scripts/design-audit.mjs` 0건, 390·1280px 캡처(합성 데이터).

## 결정

운영자가 2026-10-11에 D1–D5를 포함한 스펙 전체를 "승인 (추천)"으로 승인했다. 검토한 대안 "마이그레이션 없이(기존 '답변 저장'으로 기록)"은 고르지 않았다.

- D1(운영자 결정 2026-10-11): 세입자가 올린 사진을 필수 증빙으로 지정한다. 판정 규칙은 바꾸지 않는다.
- D2 이벤트 종류를 새로 둔다(`EVIDENCE`, 마이그레이션 0024).
  - 기존 `ANSWERED`로 기록하면 마이그레이션은 필요 없지만, 이력에 "답변 저장"으로 보여 무엇을 했는지 흐려진다.
  - 새 종류를 두는 마이그레이션은 값을 넓히기만 해서 롤백에도 안전하다.
- D3 유형마다 사진은 하나로 하고, 다시 고르면 바꾼다. 같은 사진을 여러 유형에 써도 된다.
- D4 관리자가 특정 증빙 사진을 요구하는 추가 확인 요청은 이번 범위가 아니다(후속).
  - 후속에서 정할 점: 같은 사진을 다시 고르면 아무것도 바뀌지 않아 증빙의 `createdAt`이 예전 그대로다.
  - 추가 확인 요청은 요청 뒤에 만든 증빙만 센다(`more-info.ts`). 그래서 지금 방식으로는 같은 사진을 다시 확인해도 요청이 채워지지 않는다. D4를 만들 때 이 경우를 새 제출로 기록할지 정한다.
- D5 이미 `PARTIAL`로 제출된 접수는 그대로 둔다. 새 접수부터 적용된다.
  - 구현 메모(PR 2, 독립 리뷰 반영): 이미 보낸 접수(제출 기록이 있는 접수)에는 사진 단계를 보여 주지 않는다.
    - 접힌 "추가 확인"에는 "필요한 사진 없이 보냈어요. 관리자가 확인한 뒤 다시 물어볼 수 있어요."만 둔다.
    - 보냈는지는 세입자 화면이 가진 접수(수리 문서가 있으면 보낸 것)로 바로 판단한다. 그래서 "사진 없이 제출하기" 직후에도 사진 단계가 다시 열리지 않는다.
    - 보낸 접수가 다른 길(API 등)로 다시 열려 사진이 아직 남아 있으면, 막다른 길 대신 기존 "수리 요청 제출"을 보여 준다.
    - 보낸 뒤 사진을 고르면 상태가 `IN_PROGRESS`로 돌아간다. 그러면 화면이 이를 "관리자가 추가 확인을 요청했어요"로 잘못 읽고, 관리자가 받은 요청은 다시 제출 전이 된다.
    - 보낸 뒤 사진을 더하는 길은 이 상태의 뜻을 정하는 운영자 결정 뒤에 후속으로 한다.
    - 운영자 결정(2026-10-12, "지금은 하지 않기 (추천)"): 지금은 만들지 않는다. 관리자가 특정 사진을 요청하는 기능(D4)을 만들 때 함께 정한다.
- D6(운영자 결정 2026-10-11, PR 2 설계 중 질문에 "글자 버튼으로 남기기 (추천)"): 증빙 사진 단계에 글자 버튼 "사진 없이 제출하기"를 둔다.
  - 누르면 지금처럼 `PARTIAL`("정보 부족")로 제출되고, 관리자가 경로를 직접 정한다.
  - 사진은 지울 수 없고 접수당 3장까지라, 맞는 사진이 없을 때 아무 사진이나 고르게 되는 일을 막는다.
  - 주요 버튼은 "이 사진으로 정하기" 하나다(디자인 규칙 7절, 8.1).

## 남은 위험

- 세입자가 맞지 않는 사진을 고를 수 있다. 사람이 고른 것이므로 관리자가 사진을 보고 판단해야 한다. 관리자 화면에 고른 사진의 이름을 붙이는 이유다.
- 필수 증빙을 고르는 단계가 생겨 세입자가 누르는 횟수가 늘어난다. 대신 "정보 부족"으로 끝나는 막다른 길이 없어진다.
- 실제 서비스에서 실제 사진을 다룰 때는 보관 기간과 동의(DEV-11)를 따로 정해야 한다. 지금은 합성 데이터 데모다.
- 응답 스키마가 `.strict()`라, 배포 전 번들을 연 브라우저 탭은 `photoId`가 든 응답을 읽지 못한다. PR 2를 배포한 뒤에는 열려 있던 탭을 새로고침해야 한다. 배포된 모바일 빌드는 없다.
- DB 함수(`store_ticket`)는 `core-photo:` 참조가 실제 사진인지 따로 확인하지 않는다. 확인은 애플리케이션이 한다. 기존 신뢰 모델과 같다.
- 세입자가 증빙 사진을 고른 채 대화에도 글을 쓰면 대화의 "보내기"와 "이 사진으로 정하기"가 함께 채운 파랑이 된다(디자인 규칙 7절). 두 행동을 한꺼번에 할 때만 생긴다. 할 일 영역이 열려 있을 때 대화 버튼을 어떻게 보여 줄지는 후속으로 정한다.
