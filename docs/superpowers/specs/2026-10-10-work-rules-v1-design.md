## 규칙집 공통 형식 ★

- **머리말**: `Version | Effective | Owner`, 적용 범위, 읽는 시점, 우선순위
  - 우선순위: 호스트 안전 규칙과 실제 권한 → 운영자의 현재 지시 → AGENTS.md·project_policy·ai_delivery_rules → 이 규칙집 → 스펙·계획
  - 규칙집끼리 충돌하면 project_policy 소유 표의 주인 문서가 우선한다.
- **규칙 문장**: `DEV-`/`RES-`/`REF-` ID를 붙인 명령형 문장으로 쓰고, 필요하면 이유를 한 줄 덧붙인다.
- **쓰는 내용**: 이 저장소에서만 필요한 명령·경로·결정·함정만 쓴다. 일반 상식("깨끗한 코드")은 쓰지 않는다. 판단 기준은 "이 줄을 지우면 실수가 생기는가"다.
- **분량**: 본문 250줄 이하를 목표로 한다. 세부 내용은 링크로 넘긴다. 강조(IMPORTANT)는 문서당 최대 2개다.
- **중복 금지**: 같은 내용은 소유 문서 한 곳에만 쓰고 나머지는 링크로 연결한다. 작업 절차(R01–R10)는 [AI 작성·전달 사전 규칙](../../../governance/ai_delivery_rules.md)이 소유한다.
- **문서 끝**: 자체 점검표, 변경 방법(PR로만 바꾸고 날짜와 이유를 남기며, 바뀌면 게이트가 다시 읽기를 요구함), 변경 이력

## 개발 규칙 `development/DEVELOPMENT_RULES.md`

- **DEV-01 위험도 분류**
  - 고위험:
    - DB 마이그레이션·RLS·권한 함수
    - 인증·역할·세션
    - 실제 개인정보 처리 ★
    - AI가 사용자에게 보여 주는 판단·문구를 새로 만들거나 바꾸는 작업. 프롬프트, 분류 기준, 안전 게이트가 여기에 포함된다. AI 결과 주변의 화면 배치만 바꾸는 것은 일반 등급이다 ★
    - 외부 발송·유료 서비스
    - 배포·인프라·비밀 값
    - 프레임워크·런타임 메이저 업그레이드(Next.js, Expo SDK, React, Node, PostgreSQL) ★
    - FROZEN 범위
  - 일반: 그 밖의 작업
  - 등급은 PR 본문 첫 줄에 적는다. 애매하면 고위험으로 본다. 작업 중 고위험 경로를 건드리면 다시 분류한다.
- **DEV-02 작업 크기 ★**
  - PR 하나에 목적 하나. 리팩터링은 따로 하고, 테스트는 같은 PR에 넣는다.
  - 100줄 안팎이 적당하고, 1000줄이 넘으면 나눈다. 생성 파일과 lockfile은 세지 않는다.
  - 브랜치는 2일 안에 병합하는 것을 목표로 한다. 모든 커밋에서 빌드가 깨지지 않게 한다.
- **DEV-03 일반 흐름**
  1. 최신 main에서 새 worktree를 만든다.
  2. 구현과 테스트를 함께 작성한다.
  3. DEV-06 검사를 돌린다.
  4. PR을 연다. 본문에는 등급, 목적, 실행한 검증과 결과, 남은 위험을 적는다.
  5. CI가 통과하면 끝에 리뷰를 한 번 한다.
  6. 병합한다.
  7. 사용자에게 보이는 상태가 바뀌었으면 STATUS.md를 갱신한다.
  - 리뷰는 작성한 문맥과 분리된 새 문맥에서 한다. 코드 리뷰 스킬이나 리뷰 에이전트를 쓴다.
  - 리뷰는 정확성과 요구사항 위반만 지적한다. 나머지는 Nit로 남기고 진행을 막지 않는다 ★.
  - 한 문장으로 설명되는 변경은 계획 문서 없이 진행한다 ★.
  - 단계별 영수증 파일은 만들지 않는다.
  - ai_delivery_rules R05 자체 점검은 모든 등급에 적용한다. 결과 요약은 PR 본문에 쓴다 ★.
- **DEV-04 고위험 흐름**
  1. 스펙을 쓰고 운영자 승인을 받는다. 스펙에는 위협·남용 사례와 롤백 계획을 필수로 넣는다 ★.
  2. 계획을 세운다.
  3. 실패하는 테스트부터 작성한다.
  4. 전체 검사에 Postgres·e2e 검사까지 포함해 돌린다.
  5. 새 문맥에서 독립 리뷰를 받는다.
  6. `ops/`에 수락 기록을 남긴다.
  7. 병합한다.
  - 배포·유료 서비스·계정 연결은 실행 직전에 운영자에게 확인한다.
- **DEV-05 브랜치·커밋·병합**
  - 브랜치 이름은 `feat|fix|chore|docs|test|ops/이름`으로 쓴다.
  - 커밋은 Conventional Commits로 쓴다. scope 예시: `web`, `mobile`, `db`, `domain`, `ops`, `tooling`, `research`
  - 이름을 확인한 경로만 stage한다.
  - 코드 PR은 merge commit과 `--match-head-commit`으로 병합한다. 문서만 바꾼 PR은 squash로 병합해도 된다(현행 관행). force push는 하지 않는다.
  - 다른 세션의 worktree는 건드리지 않고, 바깥 main 체크아웃에서는 작업하지 않는다.
  - 규칙 대상 파일을 셸 명령으로 우회 편집하지 않는다 ★.
- **DEV-06 필수 검사**
  - PR에서는 CI가 전체 검사를 돌린다. 병합 전에 정확한 head에서 CI가 통과해야 한다.
  - 로컬에서는 바꾼 영역에 해당하는 검사를 돌린다(ai_delivery_rules R06). 문서와 무관한 앱 전체 검사를 일부러 더하지 않는다 ★.
    - 코드: `test:shared`, `test:web`, `lint`, `typecheck`, `build:web`, `check:deps`
    - DB·persistence: `test:postgres`
    - 화면 흐름: 해당 `test:e2e:*`
    - 모바일: `test:mobile`
    - 검증 스크립트(scanner) 변경: `python tests/test_verify_repository.py`, `python scripts/tests/test_verify_repository.py`
    - 모든 변경: `python scripts/verify_repository.py --history`
  - 검사를 생략하거나 완화하지 않는다. lockfile·manifest drift도 허용하지 않는다.
  - flaky 테스트는 1회만 재실행하고, 재실행했다는 사실을 기록한다.
- **DEV-07 코드 구조**
  - 워크스페이스별 역할 표: apps/web(Next.js 16), apps/mobile(Expo 57), packages의 domain·application·api-contracts·api-client·persistence-postgres·fixtures
  - 의존 방향은 `tests/architecture/import-boundaries`가 기준이다.
  - TypeScript strict를 유지하고 기존 패턴을 재사용한다.
  - 새 프레임워크나 상태 관리 라이브러리는 결정을 거쳐야 한다.
- **DEV-08 DB·마이그레이션**
  - 번호를 붙여 추가만 한다. main에 병합된 마이그레이션은 수정하지 않는다.
  - 호환되지 않는 변경은 확장 → 이전 → 축소 3단계로 한다 ★.
  - 마이그레이션마다 Postgres 테스트를 둔다.
  - 아직 공개되지 않은 마이그레이션을 고쳤다면 로컬 fixture를 다시 만든다(알려진 함정).
- **DEV-09 보안 — OWASP Top 10:2025 대응표 ★**

  | 항목 | 규칙 |
  | --- | --- |
  | A01 접근통제 | 서버에서 권한을 검사하고 기본은 거부한다. 403 경로도 테스트한다. |
  | A02 보안 설정 | 기본값을 안전하게 둔다. |
  | A03 공급망 | DEV-10을 따른다. |
  | A04 암호화 실패 ★ | 암호화·서명·토큰은 검증된 플랫폼·라이브러리 기능(`node:crypto`, 이미 쓰는 `jose` 등)만 쓰고 직접 구현하지 않는다. 외부 연결은 TLS로 한다. |
  | A05 인젝션 | 파라미터화된 쿼리만 쓴다. |
  | A06 불안전한 설계 ★ | 고위험 스펙에 위협·남용 사례를 쓴다(DEV-04). |
  | A07 인증 | 인증 변경은 고위험이다. |
  | A08 무결성 실패 ★ | lockfile과 `npm ci`로만 설치한다. 외부에서 받은 스크립트를 검증 없이 실행하지 않는다. 신뢰할 수 없는 입력은 스키마로 검증한 뒤 쓴다. |
  | A09 로깅·경보 | 권한 거부나 인증 실패 같은 보안 이벤트는 개인정보 없이 남긴다 ★. 로그 금지 목록: 세션 값·토큰·접근 코드·비밀번호·연결 문자열·키·연락처·주소·사진 메타데이터 |
  | A10 예외 처리 | 예외가 나면 안전한 쪽으로 실패한다. |

  - 저장소·테스트·데모에는 합성 데이터만 둔다. 비밀 값은 저장소 밖에 둔다.
  - 로그인 없는 데모 진입은 합성 provider 전용 예외이며, 그 이상으로 넓히지 않는다.
- **DEV-10 의존성·공급망 ★**
  - 새 의존성을 넣기 전에 REF-06 평가를 하고 결과를 PR에 적는다.
  - 웹은 정확한 버전을 고정한다. Expo SDK 패키지는 SDK 버전에 맞춘다. `npm ci`에서 drift가 없어야 한다.
  - 새 워크플로는 `permissions`를 최소로 주고, 액션을 SHA로 고정하며, `pull_request_target`을 쓰지 않는다.
  - 의존성을 바꾸는 PR마다 `npm audit --omit=dev`를 실행하고 결과를 PR에 적는다. HIGH 이상은 이슈로 만들어 대응한다.

  - 보유기간이 끝나거나 목적을 달성하면 지체 없이, 복구할 수 없게 파기하도록 설계한다. 다른 법령 때문에 보존해야 하는 정보는 분리해 보관한다(제21조) ★.
  - 사용자에게 AI 결과를 보여주는 기능은 인공지능 기본법 제31조(2026-01-22 시행)의 사전 고지·생성물 표시 의무에 해당하는지 확인한다. [제품 AI 안전 경계](../../../product/ai_safety_boundary.md)를 따른다. [TO VERIFY: 적용 범위는 법률 확인 필요]
- **DEV-12 배포·운영**
  - [VM 데모 배포 절차](../../../deploy/vm/README.md)를 따른다.

  - 설정과 비밀 값은 환경변수로 준다 ★. 데모에는 합성 데이터만 쓴다.
  - 모니터링과 장애 알림은 실서비스 전에 필수다 ★ (후속 작업).

  - 사용자 영향, 데이터 노출, 배포 실패가 생기면 먼저 완화한다.
  - 그다음 비난 없는 짧은 사후 기록을 남긴다: 무엇이 일어났는지, 영향, 조치, 근본원인, 재발 방지
  - 같은 유형의 회귀 테스트를 추가한다.

  - 되돌리기 어려운 결정은 스펙의 "결정" 절에 맥락·결정·결과로 쓴다 ★.

  - AI 실행 로그는 AGENTS.md 규칙대로 남긴다. 일반 등급에서는 PR 하나를 "주요 단계" 하나로 본다 ★.

## 연구 규칙 `research/RESEARCH_RULES.md`

- **RES-01 시작 전**
  - 연구 질문, 이 연구가 도울 결정, 방법, 포함·제외 기준을 정한다.
  - 기존 레지스트리, 경쟁 색인, 노트를 먼저 확인한다.
  - 연구 결과는 구현 권한이 아니다. Future Product Research는 revisit gate까지 기다린다.
- **RES-02 주장 유형**: FACT, HYPOTHESIS, ASSUMPTION, DECISION, TO VERIFY와 표기법. 기존 README 내용을 그대로 옮긴다.

  - 셸 명령은 패키지 추가 명령만 확인한다. 그 밖의 셸 명령으로 하는 편집은 가로채지 않으며, DEV-05 서면 규칙이 이 부분을 맡는다.
