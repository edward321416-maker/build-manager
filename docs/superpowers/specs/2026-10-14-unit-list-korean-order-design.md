## 원인 (확인함)

1. `core_flow.units`(0026)는 `ORDER BY v.building_name, v.label, v.id`로 정렬한다. 글자 비교는 DB 기본 정렬 규칙을 따른다.
2. 시험 DB와 데모 DB는 `postgres:18.6` 이미지를 정렬 설정 없이 쓴다. 기본 규칙은 `en_US.utf8`(libc)이다. 시험 DB에서 확인했고, 데모는 같은 이미지라서 같을 것으로 본다.
3. 이 규칙은 한글을 첫 비교에서 건너뛰고, 숫자는 글자로 비교한다. 2026-10-14 시험 DB 확인 결과는 이랬다.
   - `건물 | 가나 빌라 | 대량 호실 099 | 합성 호실 1 | 나동 1호 | 지하 1호 | 가동 10호 | 10호 | 대량 호실 100 | 1001호 | 101호 | … | 2호 | … | RC1 합성 건물 A`
4. 0025 뒤에는 건물 정보가 없는 건물이 모두 `건물`이라는 이름으로 보인다. 그래서 그런 건물이 여럿이면 호실이 이름순으로 서로 섞인다(`건물 · 101호`, `건물 · 101호`, `건물 · 102호` …).

## 설계

마이그레이션 `0027_core_units_korean_order.sql` 하나

1. 정렬 규칙 `core_flow.unit_name_order`를 만든다: `CREATE COLLATION core_flow.unit_name_order (provider = icu, locale = 'ko-u-kn-true')`
   - ICU 한국어 규칙에 숫자를 값으로 비교하는 옵션(`kn`)을 더한 것이다.
   - 0025·0026과 같이 `GRANT CREATE ON SCHEMA core_flow TO bm_core_flow_owner` → `SET LOCAL ROLE bm_core_flow_owner`로 만들고, 끝에 `RESET ROLE`과 `REVOKE`를 한다. 그래서 소유자는 `bm_core_flow_owner`다.
   - 정렬에만 쓰고 색인(index)에는 쓰지 않는다. 그래서 ICU 판이 바뀌어도 색인이 깨질 일이 없다.
2. `core_flow.units(bytea)`를 0026과 같은 이름·인자·반환형·소유자·`SECURITY DEFINER`·`search_path=pg_catalog`·권한으로 `CREATE OR REPLACE`한다.
   - 바뀌는 것은 정렬 한 줄뿐이다.
   - 새 순서: `ORDER BY v.building_name COLLATE core_flow.unit_name_order, v.property_id, v.label COLLATE core_flow.unit_name_order, v.id`
   - 누가 어느 호실을 보는지, 건물 단위 권한 검사(`MATERIALIZED`), 응답 모양, 건물 이름 대체(`건물`)는 그대로다.

### 새 순서 (2026-10-14 시험 DB에서 같은 규칙으로 확인한 실제 결과)

- 호실 이름: `2호 → 10호 → 101-1호 → 101-2호 → 101-10호 → 101호 → 1001호 → 가동 2호 → 가동 10호 → 나동 1호 → 지하 1호 → Ａ동 1호 → B1호 → b2호`
- 건물 이름: `가나 빌라 → 건물 → RC1 합성 건물 A`(한글이 영문보다 앞)
- 이름이 같은 건물: 건물 id 순으로 한 건물의 호실을 모두 보인 뒤 다음 건물로 넘어간다. 예: `건물 · 101호, 건물 · 102호`(첫 건물) → `건물 · 101호, 건물 · 102호`(둘째 건물)
- 알려진 점
  - `101-1호`가 `101호`보다 앞에 온다. 기호 `-`가 한글 `호`보다 먼저 정렬되기 때문이다. 이 규칙의 정상 동작이라 그대로 둔다.
  - 이름이 같은 건물끼리는 이름으로 구별되지 않는다. 묶기만 해결하고, 구별은 건물 이름을 받는 C1 2단계가 한다.

### 바꾸지 않는 것

- 화면, API 계약, 모바일
- 다른 함수와 다른 목록(입주 초대의 빈 호실 목록, `/workspace` 호실 목록은 호실 id 순으로 쪽을 나누므로 그대로 둔다)
- DB 기본 정렬 규칙(바꾸려면 DB를 새로 만들어야 한다)

## 시험 (`tests/postgres/core-unit-list.test.ts`에 더함)

1. 한국어 순서: 한 건물에 `10호`, `2호`, `101호`, `1001호`, `가동 10호`, `가동 2호`, `나동 1호`, `B1호`를 넣으면 목록이 위 순서대로 온다. 0026에서는 실패해야 한다(RED).
2. 건물별 묶기: 이름이 같은 `건물` 두 곳에 각각 `101호`, `102호`가 있으면, 한 건물의 두 호실이 붙어서 나오고 건물 id 순이다. 0026에서는 실패해야 한다(RED).
3. 기존 순서 시험("DB 기본 규칙으로 다시 정렬한 결과와 같다")은 새 규칙(정렬 규칙과 건물 id 포함)으로 다시 정렬한 결과와 비교하게 바꾼다.
4. 정렬 규칙 `core_flow.unit_name_order`: 소유자 `bm_core_flow_owner`, 종류 ICU, 지역 `ko-u-kn`(PostgreSQL이 `ko-u-kn-true`를 이렇게 저장함)
5. 함께: `npm run test:postgres` 전체와 DEV-06 검사. 화면 시험은 CI가 돌린다.

## 롤백

- 응답 모양이 같아서, 예전 이미지로 되돌려도 동작한다. 순서만 다르다.
- 마이그레이션은 앞으로만 고친다. 되돌리려면 0026의 함수 본문을 다시 넣는 새 마이그레이션을 낸다. 정렬 규칙은 남겨도 해가 없고, 지우려면 그 마이그레이션에서 `DROP COLLATION`한다.
- 데이터는 바꾸지 않는다.

## 남은 위험

- 데모 DB가 정말 `en_US.utf8`인지는 데모에서 확인하지 않았다. 다만 이 변경은 기본 규칙과 상관없이 순서를 정한다.
- ICU 판이 바뀌면 순서가 아주 조금 달라질 수 있다(정렬에만 써서 데이터나 색인에는 영향이 없다).
