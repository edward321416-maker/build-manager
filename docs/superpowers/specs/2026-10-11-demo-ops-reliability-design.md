## 문제

1. 배포 뒤 확인을 사람이 손으로 하거나, 저장소 밖 비공개 스크립트로 한다. 다음 배포 때 같은 확인을 그대로 되풀이할 수 없다.
2. VM의 `~/redeploy.sh`는 저장소에 없다. 체크섬 확인, 롤백 아카이브 보관, 준비 확인을 사람이 따로 한다. 하나라도 빠뜨리면 되돌릴 수 없는 배포가 될 수 있다.
3. 배포와 배포 사이에 데모가 멈춰도 알 수 없다. VM 재부팅, 인증서 갱신 실패, 컨테이너 중단이 그런 경우다. 시연 직전에야 발견하게 된다.

### PR A: 점검 스크립트와 정기 확인

1. `scripts/demo-smoke.mjs`
   - 대상 주소는 환경변수 `DEMO_ORIGIN`으로만 받는다. 출력에서는 주소를 `<demo>`로 가린다. 오류 메시지도 마찬가지다.
   - HTTP 검사는 항상 한다.

     | 요청 | 기대 |
     | --- | --- |
     | `/`, `/core`, `/vendor/job` | 200 |
     | 첫 화면이 불러오는 정적 청크 하나 | 200 |
     | `/api/v2/core/access`(로그인하지 않은 상태) | 401 |
     | `/demo/landlord` | 404 (B1 모드) |
     | `/_next/image` 세 가지: 쿼리 없음, 내부 경로, 예약 도메인 URL | 404이고 이미지가 아님 |
     | HTTPS 인증서(주소가 https일 때) | 만료까지 7일 이상 |

   - 브라우저 검사는 `--http-only`가 없을 때 한다. 이미 저장소에 있는 `@playwright/test`의 Chromium을 쓰고, 새 의존성은 없다.
     - 390px에서 두 데모 진입 버튼이 보인다.
     - "관리자로 체험하기"로 들어가면 1280px에서 업무함이 열린다.
     - "세입자로 체험하기"로 들어가면 390px에서 접수 화면이 열린다.
     - 5xx 응답과 페이지 오류가 없다.
   - 선택 검사
     - `--expect-text <경로> <문자열>`(여러 번 쓸 수 있음): 그 경로가 200이고 문자열을 포함해야 한다. 배포한 변경이 실제로 나갔는지 확인할 때 쓴다. PR #113에서 업체 화면 청크를 확인한 방식이다.
     - `--write-check`: 합성 수리 요청 하나를 저장해 쓰기 경로까지 확인한다. 데모 DB에 합성 요청이 하나 생기므로 배포 직후에만 쓴다.
   - 종료 코드: 모두 통과하면 0, 하나라도 실패하면 1, 사용법 오류(주소 없음 등)는 2.
2. `.github/workflows/demo-health.yml`
   - 트리거는 매시 23분 예약 실행과 수동 실행(`workflow_dispatch`)뿐이다. 정각은 GitHub가 혼잡해 실행이 늦어질 수 있어 피한다. PR과 push에서는 돌지 않는다.
   - `permissions: contents: read`만 준다. checkout은 `persist-credentials: false`로 한다. 액션은 `app-check.yml`과 같은 커밋 SHA로 고정하고, Node는 24.21.0이다(DEV-10).
   - 이 저장소에서만 돌게 저장소 이름 조건을 둔다.
   - `npm ci` 없이 Node 내장 기능만 쓰는 `--http-only`로 실행한다.
   - 실패하면 60초 뒤 한 번 더 확인한다. 그래도 실패하면 작업이 실패하고, GitHub가 cron 줄을 마지막으로 고친 사용자에게 알림을 보낸다. 이 저장소에서는 운영자 계정이다.
   - `concurrency`로 겹쳐 돌지 않게 하고, `timeout-minutes: 10`을 둔다.
     - 연결은 받지만 응답하지 않는 데모에서는 한 번 실행에 최대 약 3분(요청마다 15초)이 걸린다.
     - 두 번 실행하고 그 사이 1분을 기다려도 제한 시간 안에 "실패"로 끝나야 알림이 간다. 시간 초과로 "취소"되면 알림이 가지 않을 수 있다(PR #114 독립 리뷰).
   - 확인 단계는 `app-check.yml`처럼 `shell: bash`(`bash -eo pipefail`)로 실행한다.
   - 주소는 저장소 비밀 값 `DEMO_ORIGIN`에서만 읽는다. GitHub는 로그에서 비밀 값을 가린다.
3. `development/DEVELOPMENT_RULES.md` 1.0.3: DEV-12의 "자동 smoke 스크립트는 아직 없다"를 스크립트와 정기 확인 안내로 바꾼다.
   - 확인 항목과 기록 요구는 그대로이므로 REF-02 비교는 생략하고, 그 사실을 PR에 적는다.
   - "실서비스 전 모니터링·장애 알림"은 후속 작업으로 남긴다.
4. `deploy/vm/README.md`에 "Checks" 절을 더한다.

### PR B: 재배포 스크립트

1. `deploy/vm/redeploy.sh`. VM의 저장소 사본 안에서 실행한다.
   - `deploy <아카이브> <sha256>`
     1. 아카이브의 sha256을 확인한다. 다르면 아무것도 바꾸지 않고 멈춘다.
     2. 여유 디스크가 아카이브 크기의 4배보다 적으면 멈춘다. 이미지를 불러오고 롤백 아카이브를 저장할 공간이다.
     3. 지금 실행 중인 이미지 ID를 읽는다. `~/demo-web-<그 ID>.tar.gz`가 없으면 먼저 저장한다. 이것이 롤백 준비다.
     4. 새 이미지를 불러온다. 실행 중인 이미지와 같으면 아무것도 바꾸지 않고 끝낸다.
     5. 웹 컨테이너만 다시 만든다(`up -d --no-deps --force-recreate web`).
     6. 180초 안에 로그에 `HOSTED_DEMO_ENSURED`와 `Ready in`이 나오고, 재시작이 0회여야 한다.
     7. 성공하면 이전·새 이미지 ID와 롤백 명령을 출력한다. 실패하면 롤백 명령을 출력하고 1로 끝난다. 자동으로 롤백하지는 않는다(결정 D3).
   - `rollback <이미지 ID>`: README의 Rollback 절차를 그대로 실행한다. 불러오기, 태그, 웹 재생성, 준비 확인 순서다.
   - 비밀 값 파일(`compose.env`, `web.env`)은 읽거나 출력하지 않고 경로만 compose에 넘긴다. 로그는 위 두 표지가 있는 줄만 출력한다.
   - 테스트를 위해 `docker` 명령을 환경변수 `REDEPLOY_DOCKER`로 바꿀 수 있게 한다. 기본값은 `sudo docker`다.
2. `deploy/vm/README.md`의 Small VM, Update, Rollback 절을 스크립트 기준으로 고친다. 손으로 하는 절차는 대체 수단으로 남긴다.
3. VM 반영은 다음 배포 때 한다. VM의 저장소 사본을 `git pull --ff-only`로 맞추고 새 스크립트로 배포한다. 실행 직전에 운영자 확인을 받는다. 기존 `~/redeploy.sh`는 새 스크립트가 한 번 성공할 때까지 지우지 않는다.

### 운영자 확인이 필요한 조작

각각 실행 직전에 따로 확인받는다.

- 저장소 비밀 값 `DEMO_ORIGIN` 등록. 제가 `gh secret set`으로 하거나 운영자가 직접 한다. 값은 출력하지 않는다.
- 첫 수동 실행(`workflow_dispatch`)으로 정기 확인이 실제 데모에서 통과하는지 본다.
- 다음 배포 때 VM 저장소 사본 갱신과 새 스크립트 사용.

## 위협·남용 사례

| 사례 | 막는 방법 |
| --- | --- |
| 데모 주소가 공개 로그나 PR에 새로 남는다 | 주소는 비밀 값과 운영자 PC의 비공개 파일에만 둔다. 스크립트가 출력에서 가리고, GitHub도 비밀 값을 가린다. 출력에 주소가 없다는 것을 테스트로 확인한다. |
| 워크플로의 토큰이나 비밀 값을 악용한다 | PR과 포크에서 돌지 않는 트리거만 쓴다. 수동 실행은 쓰기 권한이 있는 사람만 할 수 있다. 읽기 권한만 주고, 액션은 SHA로 고정하며, `pull_request_target`은 쓰지 않는다. |
| 변조되거나 손상된 아카이브를 배포한다 | sha256이 맞지 않으면 아무것도 바꾸지 않고 멈춘다. |
| 되돌릴 수 없는 배포가 된다 | 새 이미지를 불러오기 전에 실행 중인 이미지의 아카이브를 확인하고, 없으면 저장한다. 디스크가 모자라면 시작하지 않는다. |
| 비밀 값이 배포 출력에 섞인다 | 비밀 값 파일을 읽거나 출력하지 않는다. 로그에서는 두 표지 줄만 출력한다. |
| 점검이 데모에 부담을 주거나 쓰레기 데이터를 만든다 | 정기 확인은 HTTP GET 열 번 남짓이고, 브라우저와 쓰기가 없다. 쓰기 확인은 명시적으로 켤 때만 합성 문구로 한 건 만든다. |
| 잘못된 경보가 반복된다 | 실패하면 60초 뒤 한 번 더 확인하고, 그래도 실패할 때만 알린다. |
| 60일 동안 활동이 없어 정기 확인이 꺼진다 | GitHub의 동작이다. README에 적고, 다시 켜는 방법(`gh workflow enable demo-health.yml`)을 남긴다. |

## 롤백 계획

- PR A와 B는 새 파일 추가와 문서 수정뿐이다. 실행 중인 데모는 바뀌지 않는다. 되돌리려면 PR을 revert한다.
- 정기 확인만 멈추려면 `gh workflow disable demo-health.yml`을 쓴다. Actions 화면에서도 끌 수 있다. 비밀 값은 `gh secret delete DEMO_ORIGIN`으로 지운다.
- 새 재배포 스크립트가 VM에서 실패하면 기존 `~/redeploy.sh`와 README의 손 절차로 돌아간다.

## 결정

운영자가 2026-10-11에 D1에서 "GitHub Actions (추천)"을 고르고, D2–D5를 포함한 스펙 전체를 "승인 (추천)"으로 승인했다.

- D1 정기 확인 위치는 GitHub Actions 예약 실행이다.
  - 공개 저장소라 무료이고, 새 계정이 필요 없다.
  - 검토한 대안: 외부 감시 서비스(운영자가 직접 가입하고 설정해야 함), 정기 확인 없음.
  - 운영 기록(2026-10-12 10:07 KST 확인): 첫 실행(2026-10-11 11:27Z)을 포함해 예약 실행 3번이 모두 성공했다. 다만 GitHub는 매시간 예약을 듬성듬성 실행한다(약 14시간에 3번).
  - 운영자 결정(2026-10-12, "지금은 두지 않기 (추천)"): 외부 감시 서비스는 지금 두지 않는다. 합성 데이터 데모라 지금 수준으로 충분하고, 실서비스 전에 모니터링과 장애 알림을 갖춘다(DEV-12).
- D2 정기 확인은 HTTP만 한다.
  - 브라우저 설치가 없어 빠르고, 데모에 세션이나 데이터를 만들지 않는다.
  - 브라우저 검사와 쓰기 확인은 배포 직후 사람이 실행할 때만 한다.
- D3 자동 롤백은 하지 않는다. 준비에 실패하면 롤백 명령만 출력한다.
  - 1 GB VM에서는 불러오기만 4분이 넘게 걸린다.
  - 실패 원인이 설정이나 DB라면 롤백이 답이 아닐 수 있어 사람이 판단한다.
  - 대신 롤백 자체를 명령 하나로 줄인다.
- D4 데모 주소는 비밀 값 `DEMO_ORIGIN`과 운영자 PC의 비공개 파일에만 둔다. 저장소, PR, 로그에 새로 쓰지 않는다.
- D5 PR을 둘로 나눈다. A(점검 스크립트와 정기 확인)를 먼저 하고, 다음에 B(재배포 스크립트)를 한다.

## 남은 위험

- GitHub 예약 실행은 몇 분씩 늦어질 수 있다. 그래서 장애를 한 시간 넘게 늦게 알 수도 있다.
- 알림이 오는지는 운영자 계정의 GitHub 알림 설정(Actions 실패 알림)에 달려 있다.
- 브라우저 검사가 화면 문구(버튼 이름, 제목)를 기준으로 하므로, 문구를 바꾸면 스크립트도 함께 고쳐야 한다. P3(용어·상태 이름) 작업 때 확인한다.
- 실서비스용 모니터링과 장애 알림(DEV-12)은 이 작업의 범위가 아니다.
