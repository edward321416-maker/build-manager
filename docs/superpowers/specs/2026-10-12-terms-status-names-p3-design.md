# 용어·상태 이름 정리 (P3) 설계

- 날짜: 2026-10-12. 작성: Claude Opus 5.5 (Claude Code).
- 위험 등급: 일반. 화면에 보이는 이름과 문구만 바꾼다. API, DB, 권한, 서버 판단은 그대로다.
- 근거: [기능 배치·메뉴 점검](../../../research/ux/2026-10-10-menu-audit.md)의 F-10, F-13, F-15, F-16, F-19와 CLM-109, [디자인 규칙](../../../design/DESIGN_RULES.md) 8.7·10·13·14절
- 결정
  - 운영자가 2026-10-10에 순서 P1 → P2 → P3을 골랐다(CLM-112). P1(#100)과 P2(#121)는 병합됐다.
  - 운영자가 2026-10-12에 방법 A "이름표 한 벌"과 아래 이름 표("제안대로")를 승인했다.
  - 같은 날 경로·관리 방식 이름, 세 묶음 순서, 제외 항목을 포함한 이 설계 문서를 승인했다("승인 (추천)").

## 문제

2026-10-12 main(`1fd4427`)에서 다시 확인한 것이다.

- 같은 상태를 화면마다 다르게 부른다. 처리 방법을 정한 뒤의 상태가 `/core` 요약은 `확인 완료`, 끼워 넣은 결정 화면은 `임대인 지정`·`승인됨`, 옛 질문 화면은 `임대인 확인 완료`다. 출입 조건은 관리자 쪽 `세입자 재실 필요`, 업체 쪽 `세입자 입회 필요`다. 진행 이력은 직접 지정도 `추천 경로 결정`으로 적는다.
- 내부 값이 보인다. `처리 완료 · COMPLETED / ENDED/CLOSED`, 업체 전달 내용의 `난방 방식: INDIVIDUAL`, 결정 화면 제목의 전체 접수번호, `검토 문서 개정 1`, 판단 근거 목록의 `heatingType`, 직접 지정 기록의 경로 코드.
- 관리자를 옛 용어 `임대인`으로 부르는 문구가 `/core`에 끼워 넣은 질문·결정 화면에 남아 있다.
- 날짜·시간이 `2026. 10. 10. 오후 1:18:21`이다(규칙 14절: `10월 10일 (토) 오후 1:18`). 업체 화면은 `10월 7일(수)`로 괄호 앞 띄어쓰기가 없다.
- 진행 이력이 질문마다 `답변 저장`을 한 줄씩 남긴다(누수 요청에서 8줄).
- 관리자에게 맞지 않는 문구가 있다. 세입자가 사진을 고르는 단계에서도 `세입자가 아직 질문에 답하는 중이에요.`라고 한다(#121 끝 리뷰의 Nit). 관리자의 입주 연결 화면에 세입자용 `내 연결 요청` 구역과 그 빈 안내가 보인다.
- `/core` 화면 파일에 합쇼체(`~습니다`) 줄이 120개 있고, 조사 오류 `담당자은`·`최신 정보으로`가 있다.

## 방법

이름표 한 벌(운영자 승인 A안). 이름을 한 파일에 모으고, 모든 웹 화면이 그 파일만 쓴다. 화면 배치와 상태 표시의 개수·자리는 그대로 둔다.

고르지 않은 안: 처리 상태와 접수 상태를 하나로 합치기(B). P2에서 승인한 업무함 행 설계를 다시 바꿔야 한다. 점검에서 나온 곳만 고치기(C). 이름이 다시 갈라진다.

## 이름 표

| 구분 | 서버 값 | 지금 화면의 이름 | 바꿀 이름 |
| --- | --- | --- | --- |
| 처리 | `OPEN` | 접수 | 접수됨 |
| 처리 | `IN_PROGRESS` | 처리중 | 처리 중 |
| 처리 | `COMPLETED` | 처리 완료 | 처리 완료 |
| 접수 | `IN_PROGRESS` | 작성 중, 제출 전 | 제출 전 |
| 접수 | `READY_FOR_REVIEW` | 확인 대기, 검토 대기 | 결정 대기 |
| 접수 | `PARTIAL` | 추가 정보 필요, 정보 부족 | 정보 부족 |
| 접수 | `NEEDS_MORE_INFO` | 추가 확인 필요, 추가 정보 요청됨 | 추가 확인 필요 |
| 접수 | `SAFETY_ESCALATED` | 긴급 확인 필요, 안전 확인 필요 | 긴급 확인 필요 |
| 접수 | `APPROVED`, `OVERRIDDEN` | 확인 완료, 승인됨, 임대인 지정, 임대인 확인 완료 | 처리 방법 결정됨 |
| 출입 | `TENANT_PRESENT_REQUIRED` | 세입자 재실 필요, 세입자 입회 필요 | 세입자가 있을 때만 방문 |
| 출입 | `TENANT_PREAUTHORIZATION_ALLOWED` | 세입자 별도 사전 동의 허용, 세입자가 따로 동의한 시간에만 부재 중 출입 가능 | 세입자가 따로 동의한 시간에만 부재 중 출입 가능 |

- `결정 대기`는 업무함 행의 보조 글자 `처리 방법 결정 필요`와 짝이다. `정보 부족`·`접수됨`·`처리 중`은 디자인 규칙 2.3의 예와 같다.
- 제출 전 요청을 `제출 전` 하나로 보이는 P1 규칙(`DraftBadge`)은 그대로다.

이름 표에 함께 넣는 표시 이름(운영자가 승인한 "`임대인` → `관리자`"를 따른 것):

| 대상 | 바꿀 이름 |
| --- | --- |
| 경로 `LANDLORD_REVIEW` | `임대인 검토` → `관리자 검토`. 나머지는 웹 결정 화면의 선택지 이름(관리사무소, 위탁관리, 제조사 A/S, 일반 수리업체) 그대로다. 서버가 주는 추천 경로 이름(`일반 수리 업체`, `위탁 관리사`)은 선택지 이름과 달라서, 추천 경로도 이 표의 이름으로 보인다. |
| 관리 방식 `OWNER_DIRECT` | `임대인 직접 관리` → `건물주 직접 관리`. 이 값은 관리자가 아니라 건물 주인을 뜻하므로 `건물주`로 쓴다. `MANAGEMENT_OFFICE`는 `관리사무소`. |
| 난방 방식 | `INDIVIDUAL` → `개별난방`, `CENTRAL_SHARED` → `중앙·공용난방`(옛 건물 화면의 이름) |
| 건물 정보 이름 | `heatingType` 난방 방식, `managementMode` 관리 방식, `ownerSuppliedBoiler` 건물주 제공 보일러, `primaryUse` 주용도, `approvalYear` 사용승인 연도 |
| 진행 이력 `DECISION` | `추천 경로 결정` → `처리 방법 결정`(승인과 직접 지정을 모두 덮는 이름) |

## 범위

세 묶음으로 나눠 올린다. 묶음마다 목적이 하나다(개발 규칙 DEV-02).

### 묶음 1: 이름표 한 벌과 내부 값 숨기기

1. `apps/web/src/components/status-names.ts`에 위 이름 표를 모은다.
   - 서버 값마다 이름이 하나씩 있다. 타입이 서버 계약(`@build-manager/api-contracts`)의 값 목록을 그대로 따르므로, 값이 늘면 타입 검사가 실패한다.
   - 화면 코드가 서버 핵심 코드(`domain`, `application`)를 가져오지 않는다는 규칙(`tests/architecture/import-boundaries.ts`)을 지킨다.
2. 이 파일을 쓰는 곳
   - `/core`: `ui/work-status-badge.tsx`(처리·접수 이름), `core-screen.tsx`(이력 이름), `vendor-handoff-manager.tsx`(출입 이름, 공유 정보 값)
   - 끼워 넣은 옛 화면: `components/tenant/views.tsx`, `components/landlord/views.tsx`, `components/landlord/logic.ts`
   - 업체 화면: `app/vendor/job/vendor-job-screen.tsx`(출입 이름, 공유 정보 값)
3. 내부 값 숨기기
   - `처리 완료 · COMPLETED / ENDED/CLOSED · 업체 접근 종료` → `처리 완료 · 업체 접근 종료`
   - 업체 전달 내용의 공유 정보 값(관리자 미리보기, 게시된 내용, 업체 화면)은 이름 표로 바꿔 보인다. 표에 없는 값(주용도처럼 사람이 적은 글)은 그대로 보인다. 서버가 저장한 값은 바꾸지 않는다.
   - 결정 화면 제목 `수리 요청 {접수번호}` → `수리 요청 검토`. 접수번호는 지금처럼 요약 아래 `접수 세부 정보`에서 볼 수 있다.
     - 처음 정한 `처리 방법 정하기`는 끝 리뷰에서 바꿨다. 결정한 뒤와 안전 확인 요청(결정할 수 없음)에도 할 일을 시키고, P2 버튼 이름과 겹쳤다.
   - 세입자가 추가 확인에 답하는 동안 서버 상태는 `IN_PROGRESS`로 돌아간다. 결정 화면과 옛 세입자 상태 칸은 수리 요청 문서(repair packet)가 있으면 보낸 적이 있는 요청으로 보고 `추가 확인 필요`로 보인다. `/core` 요약이 진행 기록으로 하는 판단(P1)과 같은 결과다.
   - 업체 전달 내용의 출처 이름(`세입자 입력`, `건물 확인`, `관리자 확인`)과 출입 줄 이름(`출입 방식`)은 업체 화면의 이름으로 맞춘다. 관리자 미리보기가 업체가 볼 화면과 같아야 하기 때문이다.
   - 증빙 상태 이름(`필수 정보 확인됨`, `필수 정보 부족`, `정보 불일치`, `안전 위험 신호`)도 이름표에 둔다.
   - `검토 문서 개정 {n}` 줄을 없앤다.
   - 판단 근거 목록은 `heatingType` 대신 `난방 방식`처럼 이름으로 보인다.
   - 추천 경로와 직접 지정 기록은 경로 코드 대신 이름 표의 경로 이름을 쓴다(`관리자가 처리 방법을 직접 정했어요: 일반 수리업체`).
4. `/core`에 보이는 `임대인`을 바꾼다: 질문 화면의 제출 안내와 추가 정보 요청 제목, 안전 안내 문장의 `임대인·관리 주체`, 결정 화면의 `임대인 결정` 제목과 직접 선택 안내, 판단 근거의 `임대인 확인`.
   - 안전 안내 문장은 뜻을 바꾸지 않고 낱말과 말투만 바꾼다. `임대인·관리 주체에게` → `관리자나 관리 주체에게`로 관리 주체를 남기고, 안내 한 덩어리를 해요체로 맞춘다.
   - 이 묶음에서 다시 쓰는 줄은 해요체로 함께 쓴다.
5. 관리자 문구
   - 제출 전 요청의 관리자 안내(다음 할 일과 요약 문장): `세입자가 아직 질문에 답하는 중이에요.` → `세입자가 아직 제출하지 않았어요.` 질문 단계와 사진 단계를 모두 덮는다.
   - 입주 연결 화면의 `내 연결 요청` 구역은 세입자에게 늘 보이고, 관리자에게는 자기 신청이 있을 때만 보인다.
6. 조사 오류 `담당자은` → `담당자는`, `최신 정보으로` → `최신 정보로`

### 묶음 2: 날짜 형식과 진행 이력

1. `apps/web/src/lib/date-text.ts`가 규칙 14절의 글자 모양을 만든다.
   - 올해: `10월 12일 (토) 오후 2:00`. 다른 해: `2025년 3월 2일 오후 2:00`. 정오는 `오후 12:00`, 자정은 `오전 12:00`이다.
   - 1시간 안의 지난 시각: `방금`(1분 미만), `10분 전`. 앞으로의 시각(처리 예정, 방문 시간)은 늘 날짜와 시간으로 쓴다.
   - 상대 시간을 쓴 곳은 `title`에 날짜와 시간을 함께 둔다.
   - 시간대: `/core`는 지금처럼 브라우저 시간대, 업체 관련 화면은 지금처럼 서울 시간(`lib/vendor-time.ts`)이다. 두 곳 모두 같은 글자 모양 함수를 쓴다.
2. 업체 시간 글자의 괄호 앞을 띄운다: `10월 7일(수)` → `10월 7일 (수)`
3. `/core`에서 `toLocaleString`을 쓰는 곳을 모두 바꾼다: 진행 이력, 대화 메시지, 결과 확인, 업무함 처리 예정, 호실 정비 이력, 초대 시각.
4. 진행 이력 묶기
   - 같은 사람이 질문 답변이나 증빙 사진 지정을 이어서 남겼고 메시지가 없으면 한 줄로 묶는다: `세입자 · 질문 답변 8건`. 시각은 마지막 기록의 시각이다.
   - 메시지가 있는 기록(추가 확인 요청, 처리 기록)은 묶지 않는다. 처리 방법 결정도 묶지 않는다. 결정과 그 정정이 따로 보여야 하기 때문이다(구현 중 화면 시험으로 확인해 좁힘).
   - 이름: 접수 내용 저장, 질문 답변, 증빙 사진 지정, 수리 요청 제출, 추가 확인 요청, 처리 방법 결정, 처리 기록

### 묶음 3: 해요체

- 결정 화면의 `경로` 낱말(`직접 지정할 경로`, `경로 직접 지정`, `추천 경로`, `왜 이 경로인가`)을 P2·이름 표가 쓰는 `처리 방법`으로 맞춘다. 묶음 1 끝 리뷰에서 나온 것으로, 화면 시험이 이 이름으로 요소를 찾으므로 문구를 다시 쓰는 이 묶음에서 함께 바꾼다.
- `apps/web/src/app/core` 아래 화면 파일과, `/core`에 끼워 넣어 보이는 질문·결정·사진·방문 시간 컴포넌트의 합쇼체 문장을 해요체로 바꾼다(디자인 규칙 10절).
- 뜻은 바꾸지 않는다. 오류 문장은 원인과 해결을 함께 쓰는 지금 구조를 지킨다.
- 디자인 규칙 16절의 `/core` 합쇼체 항목을 지운다(#122가 16절을 고치므로 그 병합 뒤에 맞춘다).

| 날짜의 건물·세대 표기(`{동}동 {호}호`) | 호실 이름은 관리자가 적은 값을 그대로 쓴다. |

## 시험

- 단위 시험
  - 이름 표: 서버 계약의 모든 값에 이름이 있고, 이름에 영문 대문자 코드가 없다.
  - 날짜: 올해, 다른 해, 정오·자정, 방금, 59분 전, 61분 전, 앞으로의 시각, 업체 시간의 괄호 띄어쓰기.
  - 진행 이력 묶기: 연속 답변, 사람이 바뀌면 끊김, 메시지가 있으면 묶지 않음.
  - 기존 시험이 보던 이름이 바뀐 곳은 기대값을 새 이름으로 고친다. 구현을 바꾼 것이지 시험 데이터를 바로잡은 것이 아니라고 PR에 적는다(AI 작성·전달 규칙 R06).
- 화면 시험
  - `test:e2e:core`, `test:e2e:vendor`, 그리고 바꾼 이름을 보는 로그인 화면 시험
  - 결정 뒤 세 화면(요약, 결정 화면, 세입자 요약)이 같은 이름 `처리 방법 결정됨`을 보이는지, 업체 전달 내용에 `INDIVIDUAL`이 없는지 보는 시험을 더한다. 각 시험은 바꾸기 전 코드에서 실패하는 것을 확인한다.
- 디자인 점검: `scripts/design-audit.mjs` 발견 0건, 390px·1280px 화면 캡처(합성 데이터)
- 개발 규칙 DEV-06의 코드 검사 전부와 `python scripts/verify_repository.py --history`
