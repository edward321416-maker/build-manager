# 하단 탭바·왼쪽 메뉴 (P5) 설계

- 날짜: 2026-10-13. 작성: Claude Opus 5.5 (Claude Code).
- 위험 등급: 고위험(DEV-01, DEV-04).
  - 인수 때 고정한 화면 배치(FROZEN)를 바꾼다. [인수인계](../../../ops/CHAT_HANDOFF.md)에 "RC1 functional contracts and the accepted Apple/Toss/spatial/responsive UI remain frozen"이라고 적혀 있다.
  - 로그인 뒤 소속 선택과 로그아웃 자리를 옮긴다.
  - API, DB, 권한, 서버 판단은 바꾸지 않는다.
  - 순서(DEV-04): 이 스펙 승인 → 구현 계획 → 실패하는 시험 먼저 → 전체 검사(`test:postgres`, 관련 `test:e2e:*` 포함) → 새 문맥의 독립 리뷰 → `ops/` 수락 기록 → 병합. 데모 배포는 실행 직전에 운영자에게 묻는다.
  - 메뉴 점검 11절 표는 P5를 "일반 + 패키지 추가"로 적었다. 이 문서는 FROZEN 화면을 바꾸므로 고위험으로 올리고, 패키지는 더하지 않는다(7절).
- 근거
  - [메뉴 점검](../../../research/ux/2026-10-10-menu-audit.md) 9.2절의 탭 구성과 P5(메뉴 뼈대).
  - [내비게이션 규칙 설계](2026-10-10-navigation-rules-design.md)의 D1–D8.
  - [디자인 규칙](../../../design/DESIGN_RULES.md) 8.10, 8.13–8.16, 12, 13절과 16절의 내비게이션 항목.
- 범위: 웹 `/core`만. 모바일 앱의 탭바는 앱 v2 때 만든다.

## 문제 (main `7256df7`에서 코드로 확인함)

1. `/core`는 1023px 이하에서 위쪽 메뉴를 쓴다. 규칙은 767px 이하 하단 탭바, 768px 이상 왼쪽 메뉴 248px이다(8.10, 8.14).
2. 메뉴가 두 군데로 나뉘어 있다.
   - 위쪽 `작업 이동`에는 `접수`(관리자는 `업무함`)와 `입주 연결` 두 항목만 있다(`login-screen.tsx`).
   - 관리자의 `업무함 / 호실 정비 이력` 전환 버튼은 화면 안의 `관리자 보기`에 따로 있다(`core-screen.tsx`).
3. 소속 선택과 로그아웃이 1차 메뉴 위에 늘 보인다. 규칙은 이 둘을 계정 메뉴('내 정보')에 둔다(8.10, 8.16).
4. 2026-10-12 결정으로, 휴대폰 위쪽 메뉴 링크만 높이 40px이다(규칙 맨 위 [DECISION], 16절, `core-design.module.css` 767px 이하 규칙, `scripts/design-audit.mjs`의 `phoneMenu`). 탭바가 생기면 지우기로 했다.
5. 처리할 일을 한곳에서 볼 수 없다.
   - 세입자의 '내 답변 필요'는 목록 행 표시로만 보인다. 방문 시간 선택과 결과 확인은 요청을 열어야 안다.
   - 관리자의 결정 필요, 긴급 확인, 답변 대기, 기한 지남은 업무함 행과 정렬로만 드러난다.
6. Tabler 아이콘이 아직 없다. 뒤로 버튼은 글자 `← 목록으로`다.

## 목표

- 역할마다 메뉴 정의 한 벌로 767px 이하의 하단 탭바와 768px 이상의 왼쪽 메뉴를 함께 그린다. 그래서 항목, 순서, 이름, 아이콘이 늘 같다.
- 탭 '알림'에 처리할 일을 모으고, 건수를 배지로 보인다. 새 서버 기능 없이 이미 있는 응답으로 만든다.
- 휴대폰 40px 예외를 없앤다.
- 개발 접근 코드 모드(B1이 아닌 `/core`)에도 같은 메뉴를 붙인다.

## 범위 밖

- 모바일 앱(Expo)의 탭바와 안전 영역(앱 v2).
- 실제 알림 기능: 받은 기록, 읽음 상태, 푸시, 알림 설정.
- 아직 내용이 없는 계정 메뉴 행: 도움말·문의, 약관·개인정보 처리방침, 알림 설정. 빈 행은 두지 않는다(D5).
  - 그래서 메뉴 점검이 P5에 묶은 F-18(도움말·문의 없음, 영문 기본 404 화면, 파비콘 404)은 이번에 풀리지 않는다. 도움말 내용을 쓴 뒤의 후속으로 남긴다. 404 화면과 파비콘은 메뉴와 따로 고칠 수 있다.
- `/workspace` 화면의 디자인 이전. 이번에는 링크만 건다.
- 요청 상세를 주소로 바로 여는 기능(상세 딥 링크).

## 설계

### 1. 메뉴 한 벌

메뉴 정의는 순수 데이터 한 곳(새 파일 `nav-config.ts`, `apps/web/src/app/core/` 아래)에 둔다. 탭바, 왼쪽 메뉴, '더 보기' 목록, '내 정보' 목록, 주소 검사가 모두 이 정의만 읽는다.

세입자(`TENANT`)

| 순서 | 주소 `tab` | 라벨 | 아이콘 |
| --- | --- | --- | --- |
| 1 | `home` | 우리 집 | `home` |
| 2 | `requests` | 내 요청 | `clipboard-list` |
| 3 | `alerts` | 알림 | `bell` |
| 4 | `me` | 내 정보 | `user` |

관리자(`ORG_ADMIN`, `PROPERTY_STAFF`)

| 순서 | 주소 `tab` | 라벨 | 아이콘 |
| --- | --- | --- | --- |
| 1 | `work` | 업무함 | `clipboard-list` |
| 2 | `alerts` | 알림 | `bell` |
| 3 | `more` | 더 보기 | `dots` |

- 라벨은 모두 공백 포함 4자 이내다(8.14). '홈' 뜻의 탭이 맨 왼쪽이다.
- 세입자의 '내 정보'는 맨 오른쪽 탭이다. 관리자는 '더 보기'가 있어 '내 정보'가 그 목록 맨 아래다(8.14).
- 역할은 서버가 준 값만 쓴다. B1에서는 고른 소속의 역할(`CoreAccessDto.organizations[].role`), 개발 모드에서는 세션의 역할이다.

'더 보기' 목록(관리자). 주소는 `?tab=more&view=<값>`이다.

| 순서 | 행 | `view` | 보이는 역할 |
| --- | --- | --- | --- |
| 1 | 호실 정비 이력 | `maintenance` | 모든 관리자 |
| 2 | 입주 연결 | `invitations` | `ORG_ADMIN`, B1 모드 |
| 3 | 건물·호실 관리 | 없음. `/workspace`로 이동 | `ORG_ADMIN`, B1 모드 |
| 4 | 내 정보 | `me` | 모든 관리자 |

- `/workspace`는 B1 모드에서만 열리고(그 밖에는 404), 아직 옛 디자인이다. 체험 세션도 로그인 흐름과 같은 세션이라(`apps/web/src/server/b1/demo-entry.ts`) 열린다. 화면 시험이 링크 이동을 확인한다.
- 건물 담당자(`PROPERTY_STAFF`)는 지금 위쪽 '입주 연결' 링크로 세입자용 "내 호실 연결 요청" 화면을 볼 수 있다(`OnboardingPanel`의 `manager=false`). 담당자가 쓸 일이 없는 화면이라 메뉴에서 뺀다(D10).

'내 정보' 목록(계정 메뉴, 8.16). 위에서부터 이 순서다.

| 행 | 세입자 | 관리자 | 개발 모드 |
| --- | --- | --- | --- |
| 내 호실(건물과 호실 이름) | `view=units` | 없음 | 세입자만 |
| 내 소속(바꾸기) | 화면 안 선택 상자 | 화면 안 선택 상자 | 없음 |
| 호실 연결(지금의 세입자 '입주 연결') | `view=link` | 없음 | 없음 |
| 오픈소스 라이선스 | `view=licenses` | `view=licenses` | 있음 |
| 로그아웃(맨 아래) | 버튼 | 버튼 | 버튼 |

- 내 소속은 지금의 선택 상자(`내 소속`, 긴 이름을 줄바꿈해 보이는 `.core-org-current` 포함)를 그대로 옮긴다. 소속이 하나면 이름만 글자로 보인다. 이 글자 행은 PR 1b에서 넣었다. 선택 상자를 확인하는 화면 시험은 두 소속 세션으로 옮겼다.
- 소속과 호실 연결은 B1 기능이라 개발 모드에는 없다. 개발 모드에도 내 호실과 오픈소스 라이선스는 둔다. 라이선스 고지는 어느 모드에서나 닿아야 하기 때문이다(D11).
- 행 이름과 그 행 화면의 제목은 같다. 연결 패널의 지금 제목('입주 연결', '내 호실 연결 요청')은 행 이름('입주 연결', '호실 연결')에 맞춘다.
- 메뉴 안의 연결 화면은 상단 바를 하나만 둔다. '연결 상태 새로고침'은 내용 안의 버튼이다.
- 관리자의 오픈소스 라이선스는 '더 보기'가 아니라 그 안의 '내 정보'에 둔다. 규칙 8.16이 이 행을 계정 메뉴에 두기 때문이다.

### 2. 화면 뼈대

767px 이하(휴대폰)

- 1차 화면(각 탭의 첫 화면) 아래에 탭바를 고정한다.
  - 높이 56에 `env(safe-area-inset-bottom, 0px)`를 더한다. 칸 안은 위에서부터 5·아이콘 24·5·라벨(`tab`, 줄 높이 17)·5다.
  - 칸은 같은 너비이고 칸 전체가 링크다. 바탕 `surface`, 위쪽 선 `border` 1px, 그림자 없음, 층 10(6절).
  - 기본 탭은 선 아이콘과 `text-secondary`다. 선택된 탭은 채운 아이콘, `primary`, 라벨 굵기 600이다. 바뀔 때 움직임은 없다.
  - 글자를 키우면 높이도 함께 늘고 라벨을 자르지 않는다.
- 1차 화면 내용 아래에 탭바 높이만큼 여백을 둔다. 스크롤 영역의 `scroll-padding-bottom`은 탭바 높이 + 20px이다.
- 하위 화면(요청 상세, '더 보기'·'내 정보'의 행 화면)에는 탭바가 없다. 위쪽 상단 바(높이 56)에 뒤로 버튼(`chevron-left` 24, 누르는 영역 50×50, 이름 "뒤로")과 화면 제목(`subheading`)을 둔다(8.10). 지금의 글자 버튼 `← 목록으로`를 이것으로 바꾼다.
- 휴대폰의 위쪽 `작업 이동` 메뉴, 소속 선택, 로그아웃 줄은 없어진다. 40px 예외도 함께 없앤다(아래 PR 1 목록).

768px 이상

- 왼쪽 메뉴 248px. 지금은 1024px부터라, 768–1023px도 이번에 맞춘다.
  - 항목은 높이 50, 좌우 안쪽 15px, 아이콘 20, 아이콘과 라벨 사이 5, 라벨 `body`다. 왼쪽부터 읽는 줄이라 위아래만 가운데이고 글자는 왼쪽 안쪽 여백에서 시작한다(4절).
  - 현재 위치는 채운 아이콘, 굵기 600, `fill-hover` 바탕이다. 지금의 밑줄과 `fill-selected` 바탕은 쓰지 않는다.
  - 관리자는 '더 보기' 칸 없이 그 안의 1–3행(호실 정비 이력, 입주 연결, 건물·호실 관리)을 탭 항목 아래에 같은 순서로 펼친다(8.10). 아이콘은 차례로 `file-text`, `key`, `layout-grid`다(D9).
  - 맨 아래 계정 영역: 위쪽 `border` 1px 선, 현재 소속·역할 이름(`caption`, `text-secondary`, 위아래 10px), 그 아래 '내 정보' 항목. 개발 모드는 소속 대신 역할 이름만 쓴다.
- 왼쪽 메뉴에 있는 항목(탭 항목, 펼친 '더 보기' 항목, 계정 영역의 '내 정보')은 이 폭에서 1차 화면이라 뒤로 버튼이 없다(8.10). 뒤로 버튼은 그 아래 화면, 곧 '내 정보'의 행 화면(내 호실, 호실 연결, 오픈소스 라이선스)과 요청 상세에만 나온다.
- 왼쪽 메뉴에 있는 항목의 화면은 이 폭에서 1차 화면이라, 제목도 업무함·알림과 같은 크기다(767px 이하에서는 하위 화면 제목).
- 현재 위치 표시: 행 화면이 왼쪽 메뉴에 있는 항목(펼친 '더 보기' 항목, '내 정보')이면 그 항목에, 아니면 그 행이 속한 항목에 붙인다. 요청 상세에서는 세입자는 상세를 연 탭, 관리자는 업무함에 붙인다(3절).
- 넓은 화면에서 주소가 행 없이 `tab=more`이면 휴대폰과 같은 '더 보기' 목록을 보인다. 이때 왼쪽 메뉴에는 현재 위치 표시가 없다(창을 넓힌 경우에만 생김).
- 관리자의 넓은 화면 업무함은 지금처럼 목록과 상세를 나란히 보인다. 상세를 열어도 목록이 남는다.

모든 폭

- 메뉴는 `<nav aria-label="주 메뉴">` 안의 링크다. 현재 위치에 `aria-current="page"`를 붙인다(12절).
- 링크는 실제 주소(`/core?tab=…`)를 가진다. 그래서 새 탭으로 열기가 된다. 같은 창에서 누르면 페이지를 다시 불러오지 않고 화면만 바꾼다.
- 탭은 숨기거나 비활성화하지 않는다. 저장 중에도 누를 수 있고, 진행 중인 요청은 화면 뒤에서 계속된다.
- 화면 제목(`h1`): 우리 집은 지금처럼 호실 이름과 그 아래 건물 이름, 업무함은 지금처럼 "업무함", 요청 상세는 지금 제목이다. 나머지 탭과 행 화면은 그 이름이다.
- 메뉴 밖에서 화면이 바뀌어 누르던 컨트롤이 사라지면(더 보기·내 정보 행, 요청 닫기) 새 화면의 제목(h1)으로 포커스를 옮긴다. 소속을 직접 고른 뒤에도 새 화면의 제목에서 시작한다.
- 위쪽 머리글(상단 바)은 컨트롤이 한 줄이면 높이 56이고, 우리 집 머리글은 둘째 줄(건물 이름, `caption` 스타일) 때문에 그보다 높다.
- 위쪽 머리글의 '새로고침' 버튼은 그대로 둔다.
- 소속을 고르기 전 상태(불러오는 중, 로그인, 연결 확인 실패, 로그아웃 중, 소속 없음, 소속 미선택)는 지금 화면을 그대로 쓴다. 역할이 아직 없어서 메뉴를 그릴 수 없기 때문이다.
- 맨 아래 검증용 환경 안내(`EnvironmentNote`)는 내용 맨 끝, 탭바 여백 위에 남는다.

### 3. 주소와 뒤로 가기

- 주소는 `/core?tab=<탭>&view=<행 화면>`이다. 둘 다 1절 표의 값만 받는다.
  - `tab`이 없거나, 모르는 값이거나, 다른 역할의 값이면 그 역할의 첫 탭(세입자 `home`, 관리자 `work`)으로 바꾼다. 오류는 보이지 않고 `history.replaceState`로 주소를 고친다.
  - `view`가 그 탭에 속하지 않거나 그 역할에 보이지 않는 행이면 `view`를 지운다.
- 탭을 누르면 `history.pushState`로 기록을 남긴다. 그래서 브라우저 뒤로 가기가 탭 사이에서도 동작한다.
- 선택된 탭을 다시 누르면 그 탭의 첫 화면 맨 위로 간다. 열려 있던 하위 화면은 닫힌다(8.14).
- 요청 상세는 주소에 넣지 않는다. 열 때 같은 주소로 기록 하나를 남긴다(`history.state`에 상세 표시만). 요청을 연 화면의 주소는 화면 메모리에만 기억해 둔다(주소와 기록 상태에는 넣지 않는다). 그 화면의 메뉴 항목을 누르면 기록을 하나 되돌아가므로, 뒤로 가기가 같은 화면을 한 번 더 보이지 않는다. 관리자가 알림이나 호실 정비 이력에서 연 요청도 같다.
  - 브라우저 뒤로 가기(`popstate`)는 상세를 닫고 들어오기 전 탭으로 돌아간다.
  - 미전송 사진이 있으면 지금 '목록으로' 버튼처럼 닫지 않는다. 기록을 다시 넣고 기존 안내 "목록으로 돌아가기 전에 미전송 사진을 저장하거나 선택 취소해 주세요."를 보인다.
  - 새로고침하면 그 탭의 첫 화면이 나온다(상세 딥 링크는 범위 밖).
- 상세가 열린 채 다른 메뉴 항목을 누르면(넓은 화면) 상세를 닫고 그 화면으로 간다. 미전송 사진이 있으면 위와 같이 닫지 않고 안내를 보인다. 메뉴를 비활성화하지는 않는다.
- 관리자의 요청 상세는 업무함 안에 열린다(넓은 화면에서는 목록 옆). 알림이나 호실 정비 이력에서 요청을 열면 업무함으로 바뀌어 상세가 열리고(`pushState`), 뒤로 가면 원래 화면으로 돌아간다. 지금 정비 이력에서 요청을 열 때 업무함 보기로 바꾸는 동작(`openMaintenanceTicket`)과 같다.
- 세입자의 요청 상세는 연 탭 위에 열린다. 우리 집 카드, 내 요청 행, 알림 행 어디서 열어도 같은 상세다.
- 화면의 뒤로 버튼은 이 페이지 안에서 연 하위 화면이면 `history.back()`, 주소로 바로 들어온 행 화면이면 부모 화면으로 `replaceState` 한다.
- 소속을 바꾸면 그 역할의 첫 탭으로 간다(8.16). 주소는 `replaceState`로 `/core`로 바꾼다. 그 앞의 기록은 남지만, 열면 새 소속의 화면이다. 지금처럼 화면 상태는 소속마다 새로 만든다(`key`).

### 4. 탭 내용

세입자

- 우리 집(위에서부터)
  1. 결과 확인 이어하기 안내(지금의 `OutcomeRecoveryPanel`). 지금처럼 세입자 화면 맨 위에 둔다.
  2. 처리할 일이 있으면 한 줄 "처리할 일 N건 · 알림에서 보기"(알림 탭 링크)(보조 버튼 모양의 링크, 규칙 8.1).
  3. 호실 이름과 건물 이름. 호실이 여럿이면 고르는 칸.
  4. 진행 중 요청 카드 최대 3개(완료 전 요청, 처리할 일 순서 → 최근 활동 순).
     - 카드: 요청 이름(문제 · 호실), 지금 상태 표시(기존 배지), 다음 할 일 한 줄, 보조 버튼 "열기".
     - 4개 이상이면 "내 요청에서 모두 보기" 링크.
     - 다음 할 일 문구는 순수 함수 하나가 정한다. 처리할 일 이유가 있으면 그 이유, 없으면 "관리자가 확인하고 있어요."(접수됨) 또는 "처리 중이에요."(처리 중)다. 문구는 해요체이고 10절을 따른다.
     - 카드는 묶음 상자가 아니라 목록 행(규칙 8.5)이다. 구역 이름은 `진행 중인 요청`이고 제목 옆에 전체 건수를 쓴다.
     - 제출 전 요청은 상태 표시가 이미 '제출 전'이라, 다른 이유가 없으면 다음 할 일을 '아직 보내지 않았어요. 열어서 제출해 주세요.'로 쓴다(구현 계획 결정).
     - 고른 사진이 있어 행이 잠기면 우리 집·내 요청·알림 위에 '고른 사진이 있어서 요청을 열 수 없어요. 접수하거나 사진 선택을 취소해 주세요.'를 보인다.
  5. 접수 칸 "어떤 문제가 있나요?"(지금 그대로, 주요 버튼 "접수하기").
- 내 요청: 지금의 '최근 접수' 목록을 옮긴다.
  - '진행 중'과 '끝난 요청'(처리 완료) 두 묶음으로 나눈다. 행 모양은 지금 그대로다(대화 표시 포함).
  - 우리 집과 같은 호실 선택을 쓴다. 호실이 여럿이면 이 탭 위에도 같은 선택 칸을 두고, 두 탭이 한 값을 같이 쓴다.
  - 행을 누르면 상세(하위 화면)가 열린다.
- 알림: 처리할 일 목록(5절). 모든 호실의 요청을 보고, 행마다 호실 이름을 쓴다.
  - 행(8.5): 요청 이름(문제 · 호실), 이유(상태 표시, 여럿이면 모두), 최근 활동 시각(14절 형식). 연결 요청 행은 호실 이름과 "연결 요청 확인 필요"다.
  - 처음 읽는 동안은 "불러오는 중이에요"를 보이고 배지는 없다(8.11).
- 내 정보: 1절의 '내 정보' 목록.

관리자

- 업무함: 지금 업무함 그대로다. 화면 안의 `관리자 보기` 전환 버튼만 없앤다(호실 정비 이력은 '더 보기'로 옮김).
- 알림: 처리할 일 목록(5절).
- 더 보기: 1절의 '더 보기' 목록. 휴대폰에서는 목록 행(8.5)이고, 넓은 화면에서는 그 항목들이 왼쪽 메뉴에 펼쳐져 있다(2절).

빈 화면(8.11)

| --- | --- |
| 세입자 알림 | 지금 처리할 일이 없어요. 새 문제가 생기면 우리 집에서 접수해 주세요. |
| 관리자 알림 | 지금 처리할 일이 없어요. 새 요청은 업무함에 들어와요. |

### 5. 처리할 일

순수 함수 하나(새 파일 `todo-list.ts`)가 이미 불러온 데이터로 목록을 만든다. 서버를 직접 부르지 않는다. 결과는 행마다 "어느 요청(또는 연결 요청)인지, 이유 목록, 누르면 열 곳"이다.

| 이유 | 대상 | 조건 | 데이터 | PR |
| --- | --- | --- | --- | --- |
| 내 답변 필요 | 세입자 | 대화 요약 `waitingFor = TENANT`, `readOnly = false` | 대화 요약 일괄 조회 | 1 |
| 제출 전 | 세입자 | `isIntakeDraft` | 요청 목록 | 1 |
| 추가 확인 필요 | 세입자 | 처리 `OPEN`, 접수 `NEEDS_MORE_INFO` | 요청 목록 | 1 |
| 긴급 확인 필요 | 세입자 | 처리 `OPEN`, 접수 `SAFETY_ESCALATED` | 요청 목록 | 1 |
| 처리 방법 결정 필요 | 관리자 | `managerRowHint = DECIDE` | 요청 목록 | 1 |
| 긴급 확인 필요 | 관리자 | `managerRowHint = SAFETY_ESCALATED` | 요청 목록 | 1 |
| 관리자 답변 대기 | 관리자 | 대화 요약 `waitingFor = MANAGER`, `readOnly = false` | 대화 요약 일괄 조회 | 1 |
| 방문 시간 확정 필요 | 세입자 | 업체 일정 `waitingOn = TENANT` | 요청마다 업체 일정 조회 | 2 |
| 결과 확인 필요 | 세입자 | 결과 `kind = UNCONFIRMED` | 요청마다 결과 조회 | 2 |
| 업체 확인 필요 | 관리자 | 업체 전달 `waitingOn = MANAGER`, 또는 지금 배정이 업체 거절(`ENDED`, `DECLINED`)로 끝났고 아직 업체 처리 대상(`vendorHandoffEligible`)이며 처리 완료 전 | 요청마다 업체 전달 조회 | 2 |
| 기한 지남 | 관리자 | `isOverdue(item, now)` | 업무 목록 1회 | 2 |
| 연결 요청 확인 필요 | `ORG_ADMIN` | 연결 요청 상태 `REQUESTED` | 연결 요청 목록 | 2 |

- PR 1 이유와 '기한 지남'은 화면의 기존 이름 그대로다(8.7, P3 이름 표, 업무함 표시). PR 2의 새 이름 네 개(방문 시간 확정 필요, 결과 확인 필요, 업체 확인 필요, 연결 요청 확인 필요)는 같은 꼴로 짓고(앞의 것은 메뉴 점검 9.2와 2/4 설계에서 쓴 말), P3에서 만든 이름 파일(`apps/web/src/components/status-names.ts`)에 더한다.
- '제출 전'은 관리자 알림에 넣지 않는다. 세입자 차례이기 때문이다.
- 한 요청에 이유가 여럿이면 한 행에 모두 쓴다. 배지는 행 수를 센다.
  - 메뉴 점검 9.2(가설)는 세입자 배지를 답변·방문 시간·결과 확인 세 가지에만 쓰자고 했다. 이 문서는 운영자가 승인한 처리할 일 목록(D5) 전체를 센다. 모두 세입자가 해야 할 일이라 규칙 8.15("사람이 처리해야 할 건수")에 맞는다.
- 정렬: 긴급 확인 → 기한 지남 → 내 답변·관리자 답변·처리 방법 결정 → 나머지. 같은 무리 안에서는 최근 활동(요청 기록의 마지막 시각) 순이다.
- 읽는 시점: 요청 목록을 불러온 직후, 저장 같은 변경 뒤, 새로고침, 알림 탭을 열 때. 주기적으로 다시 읽지 않는다.
- 읽는 양의 한도
  - 대화 요약은 처리 완료 전 요청만, 50개씩 묶어 읽는다(서버 한도 50).
  - 요청마다 읽는 것(PR 2)은 처리 완료 전 요청(업체 일정·업체 전달)과 최근 끝난 요청 20건(결과)만, 동시에 4개까지다. 화면에 "최근 끝난 요청 20건만 확인해요"를 적는다.
  - 연결 요청 목록은 상태가 아니라 ID 순으로 20개씩 온다(`0014_core_onboarding.sql`). 그래서 5쪽(100개)까지 읽고, 더 있으면 일부만 확인했다고 알린다.
- 일부를 읽지 못하면
  - 읽은 것만 보이고, 위에 "일부를 확인하지 못했어요"와 "다시 불러오기" 버튼을 둔다.
  - 배지는 확인된 행만 센다. 그래서 건수를 부풀리지 않는다.
- 권한 응답
  - 목록 단위로 읽는 것(요청 목록, 대화 요약, 업무 목록, 연결 요청 목록)의 401·403은 지금의 다시 로그인 흐름(`onDenied`)으로 보낸다.
  - 요청마다 읽는 것(PR 2)의 403·404는 "배정 없음"으로 보고 실패로 세지 않는다. 지금 세입자·관리자 업체 화면도 이렇게 처리한다(`vendor-handoff-tenant.tsx`, `vendor-handoff-manager.tsx`). 401만 다시 로그인 흐름으로 보낸다.
- 누르면
  - 요청은 상세(하위 화면)를 연다. 상세 맨 위의 '지금 할 일'이 그 일을 보여 준다.
  - 저장 중이거나 미전송 사진을 고른 동안에는 알림 행도 내 요청 행처럼 누를 수 없다(접수 칸과 요청 상세가 같은 사진 고르기 상태를 쓴다).
  - 연결 요청은 '더 보기 › 입주 연결'을 연다.
- 배지(8.15)
  - 알림 탭에만 있다. 0건이면 없고, 99건을 넘으면 `99+`다.
  - 높이 18, 최소 너비 18, 좌우 안쪽 5, 모서리 5, 바탕 `badge`, 글자 `text-inverse`, `tab` 600 `tabular-nums`, 높이 18 안에서 세로 가운데.
  - 탭바에서는 아이콘 왼쪽 끝에서 19, 아이콘 위쪽보다 5 위. 왼쪽 메뉴에서는 오른쪽 안쪽 15px 안에 세로 가운데.
  - 링크의 화면 읽기 이름은 "알림, 처리할 일 N건"이다(0건이면 "알림").

### 6. 화면 상태 유지

- 우리 집 접수 칸, 내 요청 목록, 업무함은 늘 그려 두고 `hidden`으로 감춘다. 그래서 탭을 옮겨도 쓴 글과 고른 사진이 남는다. 연결 화면도 지금처럼 늘 그려 둔다. 정비 이력은 지금처럼 열 때만 그리고, 상태가 없는 목록 화면(알림, 내 정보, 더 보기, 내 호실, 라이선스)도 열 때만 그린다.
- 처리할 일 상태는 `CoreFlowPage` 안에 둔다. 소속을 바꾸거나 권한을 잃으면 지금처럼 화면 전체를 새로 만들어 이전 소속의 목록이 남지 않는다.

### 7. 아이콘

- 패키지를 더하지 않는다. Tabler Icons 3.49.0의 SVG 경로를 코드 한 파일(새 파일 `nav-icons.tsx`)에 옮긴다.
  - 선·채운 모양 두 벌: `home`, `clipboard-list`, `bell`, `user`, `dots`, `file-text`, `key`, `layout-grid`.
  - 선 모양만: `chevron-left`.
  - 2026-10-13에 3.49.0 패키지에서 아홉 개 모두 위 모양이 있는 것을 확인했다.
- 선 굵기는 1.5(규칙 8.13, Tabler 기본 2를 바꿈), 색은 `currentColor`, 장식용이라 `aria-hidden`이다.
- 채운 모양은 탭바와 왼쪽 메뉴의 현재 위치에만 쓴다.
- 가져온 코드에는 REF-07의 SPDX 표시를 붙인다(`SPDX-SnippetCopyrightText: 2020-2026 Paweł Kuna`, `SPDX-License-Identifier: MIT`, 출처 URL과 확인일).
- MIT 고지 전문은 '오픈소스 라이선스' 화면에 보인다(8.13).
- 이것은 [내비게이션 규칙 설계](2026-10-10-navigation-rules-design.md) 후속 1("`@tabler/icons-react`를 정확한 버전으로 고정해 추가")을 바꾼다. 아이콘이 열 개 안팎이라 패키지와 의존성 검토를 더하지 않는 편이 가볍고, 라이선스는 같다. 운영자가 방법 A(D3)와 설계 1/4(D4)에서 이 방식을 승인했다.
- 16절의 "웹은 `@tabler/icons-react`" 문장은 "웹은 쓰는 아이콘만 코드로 옮겨 씀"으로 고친다. 앱 쪽 방식(후속 2)은 앱 v2 때 정한다.
- 외부 코드를 가져오므로 PR에 REF-06 평가를 적는다.

## 위협·남용 사례

| 사례 | 막는 방법 |
| --- | --- |
| 주소의 `tab`·`view`를 바꿔 다른 역할의 화면을 엶 | 역할은 서버 응답에서만 읽는다. 표에 없는 값과 다른 역할의 값은 첫 탭으로 바꾼다. 화면을 열어도 모든 데이터 호출은 서버가 지금처럼 권한을 확인한다. |
| 처리할 일 목록으로 볼 수 없는 요청이 드러남 | 새 API가 없다. 목록은 이미 그 사용자에게 허락된 응답(세션·RLS로 걸러진 것)으로만 만든다. |
| 소속을 바꾼 뒤 이전 소속의 처리할 일이 남음 | 처리할 일 상태는 소속마다 새로 만드는 화면 안에 있다(`key`). 권한을 잃으면 지금처럼 화면을 비운다. |
| 배지가 건수를 부풀리거나 긴급한 일을 숨김 | 확인된 행만 센다. 일부 실패를 알린다. 긴급 확인을 맨 위에 둔다. |
| 요청마다 읽기가 서버에 부담을 줌 | 처리 완료 전 요청과 최근 끝난 20건만, 동시 4개, 정해진 시점에만 읽는다. 주기적으로 읽지 않는다. |
| 메뉴 링크로 바깥 주소로 보냄 | 링크는 정해진 내부 주소(`/core?…`, `/workspace`)뿐이고 주소 값으로 링크를 만들지 않는다. |
| 브라우저 기록 상태를 꾸밈 | 기록 상태에는 "상세를 열었음" 표시만 있다. 요청은 늘 서버에서 다시 읽는다. |
| 아이콘 라이선스 고지 누락 | SPDX 표시와 라이선스 화면을 시험으로 확인한다. |

개인정보: 새로 모으거나 저장하는 정보가 없다. 데모에는 합성 데이터만 쓴다.

## 롤백 계획

- DB와 API를 바꾸지 않는다. PR을 revert하면 끝난다.
- 데모는 이전 이미지로 돌린다(`deploy/vm/redeploy.sh rollback <이전 이미지>`).
- 롤백 뒤 남은 `?tab=` 주소는 예전 코드가 무시하므로 그대로 열린다.
- PR 1만 들어가고 PR 2가 문제를 일으키면 PR 2만 되돌린다. PR 1 알림은 혼자서도 동작한다.

## 남은 위험

- 기존 화면 시험 23개 파일 중 상당수가 바뀐다(테스트 절). 고정(FROZEN)된 화면을 바꾸므로 `ops/`에 이번 변경의 수락 기록을 새로 남긴다.

- 휴대폰에서 입력 중 키보드가 올라올 때 탭바 위치는 브라우저마다 다르다(iOS Safari는 키보드 뒤에 남고, 안드로이드 크롬은 키보드 위로 올라올 수 있다). 자동 시험으로는 키보드를 띄울 수 없어 실제 기기로 확인한다. 접수 칸이 가리면 운영자에게 묻고 정한다.
- 안전 영역: 지금 화면 설정(`viewport-fit` 없음)에서는 iOS Safari의 안전 영역 값이 0이다. `env()`에 기본값 0을 주어 어느 쪽이든 맞게 한다. 앱처럼 화면 끝까지 쓰는 설정은 이번에 바꾸지 않는다.
- 320px에서 글자를 200%로 키우면 "우리 집" 라벨이 칸(80px)을 넘을 수 있다. 규칙은 라벨을 한 줄로 쓰고 자르지도 않는다(8.14). 넘치면 두 줄 허용과 라벨 줄이기 중 하나를 운영자와 정한다.
- 768–1023px에서 왼쪽 메뉴 248px만큼 내용 폭이 줄어든다(768px에서 약 520px). 업무함과 상세, 접수 칸이 좁아지므로 디자인 점검과 캡처로 확인한다.
- PR 2의 요청마다 읽기는 요청이 많은 조직에서 알림 탭을 늦게 채운다. 한도와 동시 4개로 묶고, 읽은 것부터 보인다.
- 결과 확인에는 기한이 없다. 세입자가 답하지 않으면 결과가 계속 `UNCONFIRMED`라(`0017_core_ticket_outcome_followup.sql`), 오래전에 끝난 요청도 최근 끝난 20건 안이면 '결과 확인 필요'로 남는다. 운영에서 거슬리면 기간 한도를 운영자와 정한다.
- 관리자 대화 요약: 업무함이 이미 같은 요약을 읽는다(`manager-work.tsx`의 `useCommunicationSummaries`). 확인됨.
- `/workspace`는 옛 디자인이다. 메뉴에서 그 화면으로 가면 모양이 갑자기 바뀐다. 16절에 남아 있는 항목이다.
- 2-b6 세션이 PR #134에서 `join-screen.tsx`와 `core-login-e2e/design.spec.ts` 한 줄을 고치고 있다. 코드를 고치기 전에 알린다.
- 모바일 앱은 여전히 탭바가 없다. 웹과 앱의 1차 메뉴가 같아야 한다는 13절은 앱 v2 때 맞춘다.
