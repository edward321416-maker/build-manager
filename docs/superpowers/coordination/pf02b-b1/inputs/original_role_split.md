## 4. 진행 순서와 두 검토 지점

### 단계 A — Astra가 B1 계획 하나를 작성

기존 전환 명세와 직접 관련 경로·signature만 읽는다. 이미 초안이 있으면 이어서 작성하고 새 계획을 병렬로 만들지 않는다.

계획은 신원 mapping, 세션/철회, 조직 발견, 검증된 조직 context/RLS 접근 경계, API·화면, 동시 첫 로그인, 시험 범위를 함께 정한다.
이 단계에서는 제품 코드·의존성 설치·GitHub 게시를 시작하지 않는다. 현재 전환 명세의 계획 검토 조건을 유지한다.

산출물: B1 계획 `.md` 하나와 해당 파일의 SHA-256.

### 단계 B — Opus가 계획을 검토

Opus는 별도 설계안을 처음부터 다시 작성하지 않는다. 기존 계획에서 다음을 확인한다.

- 인증 전/조직 선택 전 신원·조직 조회에 필요한 DB 권한이 지나치게 넓지 않은가?
- 같은 issuer/subject의 동시 첫 로그인에 중복 User가 생기지 않는가?
- 조직·멤버십·세션 철회가 실제 데이터 접근 시 반영되는가?
- Auth0 인증과 내부 업무 권한을 섞지 않는가?
- 긍정 시험이 관리자 seed나 test-only 인증에만 기대며 실제 본체 흐름을 빠뜨리지 않는가?

판정은 `NO_BLOCKING_FINDINGS`, `CHANGES_REQUIRED`, `BLOCKED_REVIEW_ACCESS` 중 하나로 제시한다.
검토자의 동의만으로 사용자의 중요한 미결정이나 구현 실행 승인을 대체하지 않는다.

### 단계 C — 승인된 계획을 Astra가 구현

실행 승인 이후 Astra가 단일 구현 branch/worktree에서 코드·시험·수정을 소유한다.
Opus는 매 commit을 따라가며 전체 감사를 반복하지 않는다. 이미 동결한 요구사항과 검토한 경계에서 구체적인 새로운 위험이 나타날 때만 좁은 중간 검토를 요청한다.

병렬로 할 수 있는 일은 Opus의 확정 명세 기반 독립 테스트 시나리오 정리처럼 공유 상태를 변경하지 않는 작업뿐이다.
같은 파일·migration·Auth0 설정·시험 계정을 두 실행자가 동시에 수정하는 방식은 사용하지 않는다.

### 단계 D — Opus가 고정된 구현 후보를 독립 검토

Astra가 검토 대상 BASE_SHA와 HEAD_SHA를 정해 전달한다. Opus는 정확히 그 후보의 diff와 직접 의존 코드를 읽는다.
리뷰 시작 후 Astra는 대상 HEAD를 옮기지 않는다. 새 수정은 리뷰 피드백을 받은 뒤 만들고 새 HEAD로 delta 검토한다.

Opus는 소스와 증거를 대조하며 필요한 실패·권한 경계 시험만 독립 재현한다. Astra와 CI가 수행한 전체 회귀를 무조건 다시 돌리지 않는다.
재현하지 않은 항목은 `STATIC_REVIEW` 또는 `CI_LOG_INSPECTION`으로 구분한다. 소스 독립 검토를 런타임 독립 검증으로 부풀리지 않는다.

### 단계 E — Astra 최소 수정 후 delta 검토·기존 인수 절차

Astra가 확인된 결함만 수정한다. Opus는 수정된 경로·직접 영향 범위·미해결 발견사항을 확인한다.
차단 결함이 없고 필수 검사가 충족되면 이미 정한 인수/게시 절차로 진행한다. 별도 승인 없는 merge는 하지 않는다.
문구 정리·리뷰 보고서·완료 상태만을 위해 종료 PR을 연속으로 만들지 않는다.

## 5. 리뷰 결함 형식과 종료 기준

발견사항마다 아래를 기록한다.

- finding_id / severity
- reviewed_ref / file:line
- 위반한 기존 요구사항
- 실제로 가능한 입력·상태·호출 순서
- 기대 결과와 관찰 결과 또는 코드상 근거
- STATIC_REVIEW / REPRODUCED / CI_LOG_INSPECTION 구분
- 최소 수정 방향 / 아직 확인하지 못한 점

`BLOCKER/HIGH`는 현재 필수 흐름 실패, 권한 우회, 데이터 손상·누출, 필수 검증 실패 등의 근거가 있어야 한다.
취향·이름 변경·장래 확장은 `MEDIUM/LOW` backlog로 분리하고 이번 구현을 막지 않는다.
문제를 최소 몇 건 찾으라는 할당량을 주지 않는다. 근거 없는 발견을 추가하기보다 없음으로 보고할 수 있어야 한다.

같은 발견사항이 두 차례 수정 후에도 해결되지 않으면 재감사 범위를 넓히지 말고 최소 재현과 계약 차이를 조정자에게 전달한다.
이 기준은 결함을 무시하는 횟수 제한이 아니라 무한 왕복을 멈추는 상향 보고 조건이다.

## 6. 문맥·도구·쓰기 경계

- 구현과 검토는 같은 작업 디렉터리를 공유하지 않는다. Opus는 고정 commit의 별도 worktree/사본을 읽는다.
- worktree는 파일 충돌을 줄이기 위한 것이며 보안 sandbox가 아니다. 동일 Docker socket·Auth0 tenant·사용자 브라우저는 공유 상태일 수 있다.
- Opus 기본 권한은 소스 읽기와 비밀 없는 별도 리뷰 노트 작성이다. 재현 시험이 필요하면 별도 임시 DB/환경에서만 수행한다.
- CLI 버전에 실제로 존재하는 권한/plan 기능을 확인해 제한한다. 문서에 '읽기 전용'이라고 쓴 것만으로 강제 적용됐다고 주장하지 않는다.
- 신규 OAuth/MCP/M2M, 유료 플랜, 광범위 권한을 역할 분담 목적으로 추가하지 않는다.
- 계정 로그인·외부 변경이 필요한 시험은 Astra가 소유하고 한 번에 묶어서 사용자 조작을 요청한다. Opus가 같은 로그인을 다시 요구하지 않는다.
- 전체 D01 로그·skill·spec를 양쪽에 반복 복사하지 않는다. 각 실행자에게 필수 계약과 근거 위치를 전달한다.
- 새 검토자에게 hash만 주고 '이미 읽었다'고 취급하지 않는다. 필수 계약은 최초 한 번 읽고, 동일 hash라면 이후 재사용한다.
- source는 signature/diff/필요 구간부터 읽되 보안 판단에 필요한 함수와 직접 의존 경로는 생략하지 않는다.
- 테스트 raw 출력은 비공개 파일에 저장하고 요약·실패 주변만 전달한다. 민감값은 출력 전에 제거한다.
- 합격/완료는 모델 이름이 아니라 정확한 ref와 실행 증거로 판단한다.

## 7. 작은 handoff 계약

Astra → Opus:

```text
TASK: PF02-B B1
REVIEW_KIND: PLAN 또는 IMPLEMENTATION
POLICY_REF: 읽은 정책 ref
BASE_REF: 검증된 base SHA
REVIEW_REF: 구현 HEAD SHA 또는 계획 파일 SHA-256
SCOPE_DOCUMENT: 기존 전환 명세의 실제 경로
PLAN_PATH: 실제 작성된 계획 경로
CHANGED_PATHS: 해당 변경 목록
ACCEPTANCE: 이번 slice의 필수 동작과 금지 범위
CHECKS: 명령·결과·증거 위치 및 미실행 항목
KNOWN_LIMITS: 기존 위험과 제외 범위
REQUEST: 근거 있는 차단 결함만 식별, 코드 수정 금지
```

Opus → Astra:

```text
REVIEW_REF: 실제 읽은 동일 ref
VERDICT: NO_BLOCKING_FINDINGS / CHANGES_REQUIRED / BLOCKED_REVIEW_ACCESS
FINDINGS: severity·file:line·시나리오·근거·최소 수정
INDEPENDENT_TESTS: 실행한 시험만
NOT_VERIFIED: 미확인 경계
```

이 두 기록은 증거·지시서이지 외부 연결이나 merge의 자동 승인이 아니다.

## 8. 이번 파일을 전달할 때

Astra에는 이 문서와 기존 전환 명세를 전달한다. 즉시 작업은 B1 계획 하나의 작성/마무리까지다.
Opus에는 완성된 계획과 위 handoff를 전달한다. 계획이 아직 없으면 미리 같은 저장소를 탐색하며 기다리지 않는다.
역할 분담 실행·권한 설정·CLI 간 자동 전달은 이번 채팅에서 수행하지 않았다.

본 운영안의 세부 역할·검토 시점·출력 계약은 자취사무소의 기존 제약에 맞춘 제안이다.
