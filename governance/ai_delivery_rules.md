# AI 작성·전달 사전 규칙

Version: 1.0.0 | Effective: 2026-09-16 | Owner: 사용자
Canonical repository: `edward321416-maker/build-manager`
Canonical branch/path: `main` / `governance/ai_delivery_rules.md`

이 문서는 사용자가 2026-09-16 요청한 “별도 전수점검 요청 없이, 작성 전에 규칙을 확인하고 스스로 점검한 결과물을 전달”하는 운영 기준이다. 적용 대상은 이 프로젝트의 지시서, 개발 계획, 기획·조사·제출 자료, 코드 변경과 생성 파일이다. 간단한 대화까지 긴 점검 절차로 만들지는 않는다.

상위 호스트 규칙과 실제 권한이 우선한다. 이 문서는 도구 설치, 외부 공개, 계정 연결, 파괴적 작업을 독자적으로 허가하지 않는다. [프로젝트 정책](project_policy.md), [에이전트 시작 문서](../AGENTS.md), 현재 사용자가 승인한 작업을 함께 따른다.

## R01. 작성 전에 읽을 자료와 기준 버전

새 작업의 본문을 작성하기 전에 GitHub 연결로 `main`의 `AGENTS.md`, 이 문서, `governance/project_policy.md`를 확인한다. 규칙을 읽은 main 커밋을 `POLICY_REF`로 기록한다. 동일 작업 중에는 같은 버전의 읽은 내용을 재사용하고, 새 작업·규칙 변경·범위 변경 때 다시 확인한다. 도구 스키마나 이미 읽은 파일을 무의미하게 반복 출력하지 않는다.

제품·코드 사실은 별도의 `TARGET_REF`에서 확인한다. 선택된 작업 브랜치의 상태 문서, 해당 Spec/Plan, 직접 관련 계약·manifest·검증 스크립트를 필요한 범위만 읽는다. main의 오래된 제품 문서를 feature 브랜치의 최신 명세 대신 사용하지 않는다. 파일명·심볼·필요한 구간부터 찾고, 변경 대상 외 전체 소스 덤프를 피한다.

규칙을 읽기 위해 작업 브랜치를 merge/rebase/reset하지 않는다. SHA가 고정된 작업자는 지시서에 기록된 `POLICY_REF`의 규칙을 읽기 전용으로 확인하고 `TARGET_REF`는 보존한다. 새 규칙이 이미 승인된 실행 조건과 충돌하면 관련 부분만 중단·보고하며 자동 적용하지 않는다.

원격 내용과 로컬 미공개 작업을 구분한다. 원격 HEAD 확인만으로 로컬 트리·다섯 커밋·테스트 결과까지 독립 검증했다고 말하지 않는다. 규칙 조회가 불가능하면 그 사실과 마지막 확인 버전을 밝히고, 준비 가능한 초안만 `DRAFT_UNVERIFIED`로 제공한다. 읽지 않은 규칙을 읽었다고 쓰지 않는다.

## R02. 중요한 결정만 사용자 인터뷰

이미 답한 선택과 승인된 범위를 다시 묻지 않는다. 새로운 제품 범위, 역할·사용 흐름, API/DB 경계, 안전·개인정보 처리, 제출 전략, 비용·권한, 파괴적 작업, 검증 수준 변경은 실행 전에 짧은 인터뷰로 결정한다.

한 번에 핵심 결정 하나를 묻는다. 선택지별 이점·비용·영향과 추천 이유를 제시하고 답을 기록한다. 긴 작업이라는 이유만으로 불필요한 확인을 추가하지 않는다. 파일명·변수명·기존 패턴 안의 구현 세부는 별도 인터뷰 없이 처리한다.

결정 기록에는 결정 내용, 사용자 승인 근거, 적용 범위, 유지할 조건을 적는다. 중요한 미결정이 있으면 `DECISION_REQUIRED`이며, 추천안을 승인된 결정처럼 넣은 실행 지시서를 전달하지 않는다.

## R03. 범위 고정과 점검 종료

기본 흐름은 `Preflight → 작성 → 자체 점검 → 필요한 수정 → Delta 검증 → 전달`이다. 사용자가 다시 “전수점검”이라고 말해야 점검을 시작하는 구조를 금지한다.

이미 FROZEN인 범위는 새로운 재현 결과, 직접 확인한 계약 모순 또는 구체적인 안전·정보 노출 증거가 있을 때만 관련 부분을 다시 연다. 더 깔끔한 설계나 미래의 가능성만으로 재설계하지 않는다.

| 분류 | 판단과 처리 |
| --- | --- |
| BLOCKER | 승인·필수 입력·권한이 없거나 필수 검증이 실패해 현재 작업을 안전하게 진행할 수 없음. 관련 범위 중단. |
| HIGH | 현재 필수 흐름 실패, 계약 위반, 데이터 손상·노출 등 직접 근거가 있는 결함. 승인된 범위 안에서 최소 수정하거나 필요한 결정만 질문. |
| MEDIUM / LOW | 현재 인수조건을 막지 않는 개선·미래 위험. 기존 backlog에 기록하고 작업 범위를 늘리지 않음. |

자체 점검에서 발견한 같은 범위의 오류는 전달 전에 고친다. 수정 후에는 변경 부분과 의존 인터페이스 및 표준 회귀만 확인한다. 새로운 근거 없이 전체 감사를 반복하지 않는다. 전체 시스템 감사는 미리 정한 milestone에서만 한다. 반복 횟수 제한을 이유로 실제 BLOCKER/HIGH를 숨기지도 않는다.

## R04. 지시서에 필요한 최소 계약

실행 지시서는 아래 항목을 빠짐없이 갖되, 변하지 않는 규칙 전문은 복사하지 않고 `POLICY_REF`로 연결한다.

- 작업 목표, `TARGET_REF`, 시작 전 상태, 완료 판정과 다음 작업의 중단 지점.
- 허용 파일·코드 범위와 문서·로그·테스트 설정 예외. 금지 범위와 승인된 결정.
- 실제 존재하는 API/DTO/함수/경로, 입력·출력·오류·상태 경계. 미확인 항목은 미확인으로 표시.
- 단계별 실행·검증 명령, 실행 디렉터리·셸·환경변수, 예상 결과, 실패 시 처리.
- 커밋·공개 권한, 데이터 보호, 변경 후 검증, 결과 보고 형식.

manifest의 선언과 실제 설치·실행을 구분한다. 스택을 알아보기 위해 manifest 스크립트를 실행하지 않는다. 버전 의존 명령은 설치된 CLI 도움말 또는 해당 버전의 공식 문서로 확인한다. 의존성 추가 없음과 manifest 변경 없음은 서로 다른 조건이다.

기준 SHA가 있는 지시서를 잇는 후속 작업에서는 새 SHA를 실제 조회해 갱신한다. 이전 보고의 SHA를 무조건 재사용하거나 현재 브랜치에 원격 조회를 적용한 것처럼 꾸미지 않는다.

## R06. 검증은 실제 대상을 검사

테스트 성공은 typecheck·lint·build 성공을 대신하지 않는다. manifest에서 관련 표준 gate를 확인하고 작업별로 적용 여부를 정한다. 필수 gate를 조용히 빼거나 낮추지 않는다. 문서 작업에 무관한 앱 전체 테스트를 무조건 추가하지도 않는다.

회귀 테스트는 유효한 사전 상태에서 목표 동작이 실패하는 것을 보여야 한다. 아직 없는 import 때문에 실패한 결과를 행동 회귀의 RED 증거로 포장하지 않는다. 요청 두 개, 서로 다른 인스턴스, 모듈 재평가 등 주장하는 경계를 실제로 시험한다. 단순 mock 호출 확인과 실제 경로·API·화면 실행을 구분한다.

테스트 기대를 고칠 때는 구현 변경인지 잘못된 fixture 교정인지 기록한다. 테스트 개수만 채우지 않는다. fake timer, 환경변수, 작업 디렉터리 등 임시 변경은 기존 값을 보존해 finally에서 복원한다. 테스트·export·번들·에뮬레이터·실기기 검증을 같은 증거로 취급하지 않는다.

기존 실패는 baseline 사실로 기록한다. 문서의 부분 검증을 저장소 전체 PASS로 표현하지 않는다. 현재 작업에 적용되는 필수 gate가 실패하면 성공 판정과 해당 공개를 보류한다. 범위 밖 실패가 있다는 이유만으로 별도의 승인된 문서 작성까지 자동 재설계하지 않는다.

## R07. 공개 전 데이터·Git 검사

프로젝트 검출기의 해당 버전과 실제 검사 대상을 먼저 읽는다. staged index, working tree, reachable history는 서로 다른 대상이다. 검출기가 index를 읽으면 commit 전 후보 index를 검사하고, history gate가 있으면 모든 대상 히스토리도 확인한다.

합성 테스트라도 완성된 credential URL, 이메일, 토큰 형태가 검출되면 정상적인 공개 gate 실패로 처리한다. 거절 동작 테스트에는 명백히 비밀이 아닌 합성 조각의 런타임 조립 등 검출기와 양립하는 표현을 사용한다. 진짜 비밀을 분할·인코딩해 숨기는 것은 금지한다. 오류 문자열을 지시서나 로그에 복사해 같은 문제를 재생산하지 않는다. 검출기 예외나 완화는 임의로 추가하지 않는다.

Git 수정은 승인된 저장소·브랜치·범위에서만 한다. 이름을 확인한 경로만 stage하고, 이전 작업을 보존한다. 원격 쓰기 직전 대상과 동시 변경을 확인하고 쓰기 후 정확한 ref·내용을 재조회한다. 일반 push, 파일 API 쓰기, PR, merge를 구분해 보고한다.

히스토리 재작성·삭제는 기본 금지다. 사용자에게 정확한 대상과 작업을 명시해 승인받은 일회성 예외만 적용한다. 그 예외가 future 작업의 일반 권한이 되지 않는다. tree 보존을 약속했다면 전후 tree SHA를 실제 비교한다. refs·stash·다른 worktree·원격 추적 ref가 검사 범위에 미치는 영향을 확인하고 사용자 ref를 자동 삭제하지 않는다. reflog에 남은 객체와 공개 히스토리에서 도달 가능한 객체를 구분하며 “영구 삭제”를 함부로 주장하지 않는다.

## R08. 파일 생성과 버전 관리

스크립트의 문자열 치환은 대상 존재와 치환 횟수를 확인한다. 조용히 실패한 치환 결과를 최종본으로 전달하지 않는다. 마지막 편집 이후 파일을 다시 읽어 존재·크기·UTF-8·필수 내용·구조·링크를 확인하고 필요한 SHA-256을 계산한다. 생성 호출이 실패하면 파일과 해시가 생겼다고 추정하지 않는다.

사용자에게 전달하는 파일 링크는 현재 실행 환경에 실제 존재하는 경로만 사용한다. GitHub 업로드는 성공 응답과 원격 재조회로 확인한다. 코드 변경 전달은 Unified Diff 또는 정확한 SEARCH/REPLACE 형식을 유지한다.

작업 중 내부 수정은 자체적으로 모아 검증하고, 사용자에게는 전달 가능한 한 버전과 짧은 변경 요약을 준다. 내용·범위가 바뀌면 새 revision과 supersedes를 기록하되, 의미 없는 FINAL/vN 이름 반복을 만들지 않는다. 이전 파일을 사용자 승인 없이 삭제하지 않는다.

## R09. 전달 상태와 짧은 증거 기록

`READY_TO_SEND`는 지시서·자료의 자체 점검 완료이며 구현 성공이 아니다. `IMPLEMENTATION_VERIFIED`는 실제 실행 결과가 인수조건을 충족한 경우다. `BLOCKED`, `DECISION_REQUIRED`, `DRAFT_UNVERIFIED`, `NOT_RUN`, `PENDING_SYNC`는 실패·불확실성을 숨기지 않기 위한 별도 상태다.

지시서 또는 동반 검증 기록에는 다음 최소 항목을 남긴다.

```text
POLICY_REF: 읽은 규칙 커밋 또는 파일 해시
TARGET_REF: 대상 저장소와 작업 SHA; 로컬은 보고/독립확인 구분
DECISIONS: 승인 근거와 적용 범위
SCOPE: 허용 / 금지 / 문서·테스트·로그 예외
CHECKS: 실행 명령과 결과; 문서 검토와 NOT_RUN 구분
STATUS: READY_TO_SEND / DECISION_REQUIRED / BLOCKED / DRAFT_UNVERIFIED
ARTIFACT: 실제 경로 또는 원격 파일; 최종 해시가 필요한 경우 실제 계산값
```

일반 응답에는 긴 점검표를 반복하지 않는다. 짧은 결과·중요한 제한·바로 사용할 결과물만 전달하고 상세 근거는 해당 문서 또는 기존 검증 로그에 둔다. `CHECKPOINT | 작업 | evidence=실제 근거 | tokens=unknown/estimated` 형태를 사용할 수 있다. tokens 수치를 측정하지 않았다면 측정값처럼 쓰지 않는다.

## R10. 기록·동기화·적용의 한계

관련 skill을 사용한 뒤와 주요 작업 후 [실행 로그](../ops/AI_Execution_Log.csv)에 실제 사건만 append한다. 승인된 기록·캐시 목적지를 사용하고 중복 event_id를 피한다. Google 동기화나 스키마 캐시는 권한과 쓰기 후 확인이 있어야 synced다. 연결이 없으면 가능한 로컬 큐와 [대기 기록](../ops/pending_external_sync.md)에 pending으로 남긴다. 목적지 ID나 인증 정보는 공개 문서에 복사하지 않는다.

이 파일과 AGENTS/CLAUDE 연결은 저장소의 운영 규칙이다. 파일 존재만으로 모든 채팅이나 CLI가 읽었다는 실행 증거가 되지 않는다. host 설정·hook·CI 강제 적용은 실제 설정하고 시험했을 때만 주장한다. 새 대화나 다른 실행기에는 이 저장소의 규칙 위치를 전달해야 할 수 있다. 이 프로젝트 작업자는 읽은 POLICY_REF를 남겨 준수 여부를 확인 가능하게 한다.
