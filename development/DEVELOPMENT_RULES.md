# 개발 규칙

Version: 1.0.0 | Effective: 2026-10-10 | Owner: 운영자

- **적용**: 코드·설정·테스트·스크립트·배포 파일과 `docs/` 문서를 바꾸는 작업. 패키지 추가 명령(`npm install <이름>` 등)도 포함한다.
- **읽는 시점**: 개발 작업을 시작하기 전에 이 문서 전체를 읽는다. 읽기 전 차단 게이트가 설치된 환경에서는 읽지 않으면 위 편집과 패키지 추가가 막힌다.
- **우선순위**: 호스트 안전 규칙과 실제 권한 → 운영자의 현재 지시 → [AGENTS.md](../AGENTS.md)·[프로젝트 정책](../governance/project_policy.md)·[AI 작성·전달 사전 규칙](../governance/ai_delivery_rules.md) → 이 문서 → 스펙·계획
- **다른 규칙과의 관계**
  - 작업 절차(사전 읽기, 결정 인터뷰, R05 자체 점검, 전달 상태)는 AI 작성·전달 사전 규칙이 정한다.
  - 화면 작업은 디자인 규칙(`design/DESIGN_RULES.md`)을 함께 따른다.
  - 외부 코드·라이브러리는 레퍼런스 규칙(`references/REFERENCE_RULES.md`)을 함께 따른다.
  - 연구 자료와 개인정보 원본은 [연구 규칙](../research/RESEARCH_RULES.md)을 함께 따른다.
- **근거**: [설계](../docs/superpowers/specs/2026-10-10-work-rules-v1-design.md), [외부 기준 비교](../docs/superpowers/specs/2026-10-10-work-rules-v1-benchmark.md)

## DEV-01 위험도 분류

- 작업을 시작할 때 등급을 정하고 PR 본문 첫 줄(`Risk tier`)에 적는다.
- 애매하면 고위험으로 본다. 작업 중 고위험 대상에 닿으면 다시 분류한다.

| 등급 | 대상 |
| --- | --- |
| 고위험 | DB 마이그레이션·RLS·권한 함수 |
| 고위험 | 인증·역할·세션 |
| 고위험 | 실제 개인정보 처리 |
| 고위험 | AI가 사용자에게 보여 주는 판단·문구를 새로 만들거나 바꾸는 작업. 프롬프트, 분류 기준, 안전 게이트를 포함한다. |
| 고위험 | 외부 발송(문자·카카오·푸시·메일)과 유료 서비스 |
| 고위험 | 배포·인프라·비밀 값 |
| 고위험 | 프레임워크·런타임 메이저 업그레이드(Next.js, Expo SDK, React, Node, PostgreSQL) |
| 고위험 | [STATUS.md](../STATUS.md)의 FROZEN 범위 |
| 일반 | 그 밖의 작업. AI 결과 주변의 화면 배치만 바꾸는 것도 일반이다. |

## DEV-02 작업 크기

- PR 하나에는 목적 하나만 담는다. 리팩터링은 기능 추가·버그 수정과 따로 낸다. 관련 테스트는 같은 PR에 넣는다.
- 변경 규모는 100줄 안팎이 적당하다. 1000줄이 넘으면 나눈다. 생성 파일과 lockfile은 세지 않는다.
- 브랜치는 2일 안에 병합하는 것을 목표로 한다. 모든 커밋에서 검사가 깨지지 않게 한다.

## DEV-03 일반 등급 흐름

1. 최신 `origin/main`에서 새 worktree와 브랜치를 만든다.
2. 구현과 테스트를 함께 작성한다. 한 문장으로 설명되는 변경은 계획 문서 없이 바로 한다.
3. DEV-06 검사를 돌린다.
4. PR을 연다. 본문에는 등급, 목적, 실행한 검사와 결과, 남은 위험을 쓴다.
5. CI가 통과하면 끝에 리뷰를 한 번 한다.
   - 작성한 문맥과 분리된 새 문맥에서 한다. 코드 리뷰 스킬이나 리뷰 에이전트를 쓴다.
   - 정확성과 요구사항 위반만 지적한다. 나머지는 `Nit`로 남기고 진행을 막지 않는다.
   - 이 리뷰는 작업 규칙이며 GitHub 승인 요건은 아니다.
6. 병합한다. 사용자에게 보이는 상태가 바뀌었으면 [STATUS.md](../STATUS.md)를 갱신한다.

- 단계별 영수증 파일(`ops/*_checkpoint.md` 등)은 만들지 않는다.
- R05 자체 점검(AI 작성·전달 사전 규칙)은 모든 등급에 적용한다. 결과 요약은 PR 본문에 쓴다.

## DEV-04 고위험 흐름

1. 스펙을 쓰고 운영자 승인을 받는다. 스펙에는 위협·남용 사례(누가 어떻게 악용할 수 있나)와 롤백 계획을 반드시 넣는다.
2. 구현 계획을 쓴다.
3. 실패하는 테스트부터 쓴다. 목표 행동이 실제로 실패하는 것을 확인한 뒤 구현한다.
4. DEV-06의 해당 검사에 더해 `test:postgres`와 관련 `test:e2e:*`까지 돌린다.
5. 새 문맥에서 독립 리뷰를 받는다.
6. `ops/`에 수락 기록을 남긴다.
7. 병합한다.

- IMPORTANT: 배포, 유료 서비스, 계정 연결, 데이터 삭제는 실행 직전에 운영자에게 확인한다.

## DEV-05 브랜치·커밋·병합

- **브랜치 이름**: `feat|fix|chore|docs|test|ops/짧은-이름`
- **커밋**
  - Conventional Commits로 쓴다. scope 예: `web`, `mobile`, `db`, `domain`, `ops`, `tooling`, `research`
  - 이름을 확인한 경로만 stage한다. `git add -A`는 쓰지 않는다.
- **병합**
  - 코드 PR은 `gh pr merge --merge --match-head-commit <SHA>`로 병합한다. 문서만 바꾼 PR은 squash해도 된다.
  - force push와 히스토리 재작성은 하지 않는다.
- **다른 작업 보호**
  - 다른 세션이 쓰는 worktree와 브랜치는 건드리지 않는다. `git worktree list`로 확인한다.
  - 바깥 폴더의 main 체크아웃에서는 작업하지 않는다.
  - 규칙 대상 파일을 셸 명령(sed, 리디렉션 등)으로 우회 편집하지 않는다. 편집 도구를 쓴다.

## DEV-06 필수 검사

- PR에서는 CI(`.github/workflows/app-check.yml`, `repository-check.yml`)가 전체 검사를 돌린다. 병합 전에 정확한 head에서 CI가 통과해야 한다.
- 로컬에서는 바꾼 영역에 해당하는 검사만 돌린다(AI 작성·전달 사전 규칙 R06). 실행한 명령과 결과를 PR에 적는다.

| 바꾼 영역 | 명령 |
| --- | --- |
| 모든 변경 | `python scripts/verify_repository.py --history` |
| 코드 | `npm run test:shared`, `npm run test:web`, `npm run lint`, `npm run typecheck`, `npm run build:web`, `npm run check:deps` |
| DB·persistence | `npm run test:postgres` |
| 화면 흐름 | 해당하는 `npm run test:e2e:web`·`test:e2e:core`·`test:e2e:sdk`·`test:e2e:vendor`·`test:e2e:b1` |
| 모바일 | `npm run test:mobile` |
| 저장소 검사기 | `python tests/test_verify_repository.py`, `python scripts/tests/test_verify_repository.py` |

- 검사를 생략하거나 기준을 낮추지 않는다.
- `npm ci` 뒤에 `package.json`·`package-lock.json`·`apps/mobile/package.json`·`apps/mobile/app.json`이 바뀌면 안 된다.
- 일시적으로 실패하는(flaky) 테스트는 1회만 재실행하고, 재실행 사실을 PR에 적는다. 다시 실패하면 고치거나 이슈로 남긴다.
- 검사 결과는 종료 코드나 결과 문구로 확인한다. `| tail` 같은 파이프로 실패를 가리지 않는다.

## DEV-07 코드 구조

| 위치 | 역할 |
| --- | --- |
| `apps/web` | Next.js 16 웹. 서버 코드는 `src/server/`, API는 `src/app/api/`에 둔다. |
| `apps/mobile` | Expo 57(React Native) 앱 |
| `packages/domain` | 순수 도메인 규칙. 런타임 의존성이 없다. |
| `packages/application` | 유스케이스. `domain`에만 의존한다. |
| `packages/api-contracts` | 웹·모바일·서버가 공유하는 API 계약(zod) |
| `packages/api-client` | 브라우저와 React Native에서 쓰는 HTTP 클라이언트. `api-contracts`에만 의존한다. |
| `packages/persistence-postgres` | PostgreSQL 저장소와 `migrations/` |
| `packages/fixtures` | 합성 데이터 |

- **의존 방향과 금지 import**: 기준은 [`tests/architecture/import-boundaries.ts`](../tests/architecture/import-boundaries.ts)다. 이 테스트가 검사하는 것:
  - 클라이언트 코드는 서버 코어(`application`·`domain`·`fixtures`)를 import하지 않는다.
  - 패키지별 런타임 의존성은 허용 목록으로 제한된다.
  - API 라우트의 런타임 규칙: edge 금지, Node 런타임과 dynamic 선언 필요
- TypeScript `strict`를 유지한다. 기존 패턴을 먼저 찾아 따른다.
- 새 프레임워크나 상태 관리 라이브러리는 운영자 결정을 거쳐야 한다.

## DEV-08 DB·마이그레이션

- 마이그레이션은 `packages/persistence-postgres/migrations/NNNN_이름.sql` 형식으로 추가만 한다. main에 병합된 마이그레이션은 고치지 않는다.
- 호환되지 않는 스키마 변경은 세 단계로 나눈다: 확장(새 구조 추가) → 이전(모든 코드 전환) → 축소(옛 구조 제거)
- 마이그레이션마다 `tests/postgres/`에 테스트를 둔다.
- 아직 병합되지 않은 마이그레이션을 고쳤다면 로컬 fixture를 다시 만든다(DEV-15).

## DEV-09 보안 — OWASP Top 10:2025

| 항목 | 규칙 |
| --- | --- |
| A01 접근통제 | 권한은 서버에서 검사하고 기본은 거부한다. 권한이 없을 때(403)의 경로도 테스트한다. |
| A02 보안 설정 | 기본값을 안전하게 둔다. 디버그·개발용 설정을 배포에 남기지 않는다. |
| A03 공급망 | DEV-10을 따른다. |
| A04 암호화 실패 | 암호화·서명·토큰은 검증된 기능(`node:crypto`, 이미 쓰고 있는 `jose` 등)만 쓰고 직접 구현하지 않는다. 외부 연결에는 TLS를 쓴다. |
| A05 인젝션 | SQL은 파라미터화된 쿼리만 쓴다. 사용자 입력을 문자열로 이어 붙이지 않는다. |
| A06 불안전한 설계 | 고위험 스펙에 위협·남용 사례를 쓴다(DEV-04). |
| A07 인증 | 인증·세션 변경은 고위험 작업이다. |
| A08 무결성 실패 | lockfile과 `npm ci`로만 설치한다. 내려받은 스크립트를 검증 없이 실행하지 않는다. 신뢰할 수 없는 입력은 스키마로 검증한 뒤 쓴다. |
| A09 로깅·경보 | 권한 거부, 인증 실패 같은 보안 이벤트는 개인정보 없이 기록한다. 로그에 남기지 않는 것: 세션 값, 토큰, 접근 코드, 비밀번호, 연결 문자열, 키, 연락처, 주소, 사진 메타데이터 |
| A10 예외 처리 | 예외가 나면 안전한 쪽(거부·중단)으로 실패한다. 내부 정보를 노출하지 않는다. |

- 저장소·테스트·데모에는 합성 데이터만 둔다. 비밀 값은 저장소 밖에 둔다.
- 로그인 없는 데모 진입은 합성 provider 전용 예외다. 실제 provider로 넓히지 않는다.

## DEV-10 의존성·공급망

- 새 의존성을 넣기 전에 레퍼런스 규칙 REF-06 평가를 하고 결과를 PR에 적는다. 이미 있는 의존성으로 해결되면 추가하지 않는다.
- **버전**
  - 웹은 정확한 버전으로 고정한다.
  - Expo SDK 패키지는 `npx expo install`로 SDK 버전에 맞춘다.
  - 실행 환경은 CI와 같은 Node 24.21.0, npm 11.19.0이다.
- 의존성을 바꾸는 PR마다 `npm audit --omit=dev`를 실행해 결과를 PR에 적는다. HIGH 이상은 이슈로 만들어 대응한다.
- 새 워크플로는 `permissions`를 최소로 둔다. 액션은 커밋 SHA로 고정하고, `pull_request_target`은 쓰지 않는다.

## DEV-11 개인정보·AI 기능

- **개인정보**
  - 실제 개인정보를 다루는 기능은 수집·이용 목적, 수집 항목, 보유·이용 기간, 동의 거부권과 거부 시 불이익을 고지한다(개인정보 보호법 제15조 제2항).
  - 보유기간이 끝나거나 목적을 이루면 지체 없이, 복구할 수 없게 파기하도록 설계한다. 다른 법령 때문에 보존해야 하는 정보는 분리해 보관한다(제21조).
- **AI 기능**
  - AI 결과를 사용자에게 보여 주는 기능은 인공지능 기본법 제31조(2026-01-22 시행)의 사전 고지·생성물 표시 의무에 해당하는지 확인한다. [TO VERIFY] 적용 범위는 법률 확인이 필요하다.
  - [제품 AI 안전 경계](../product/ai_safety_boundary.md)를 따른다.

## DEV-12 배포·운영

- 데모 배포는 [VM 배포 절차](../deploy/vm/README.md)를 따른다. 데모에는 합성 데이터만 쓴다.
- 설정과 비밀 값은 환경변수로 넣는다. 이미지나 저장소에 넣지 않는다.
- **롤백**: 배포 전에 직전 이미지 아카이브를 보관한다. 검증된 롤백 절차는 아직 문서에 없다. [TO VERIFY] 롤백이 필요해지기 전에 절차를 시험하고 `deploy/vm/README.md`에 적는다.
- **배포 후 확인**: 첫 화면, 로그인 없는 데모 진입, 핵심 화면 하나를 직접 열어 보고 결과를 PR이나 STATUS.md에 적는다. 자동 smoke 스크립트는 아직 없다.
- 실서비스 전에는 모니터링과 장애 알림을 갖춘다(후속 작업).

## DEV-13 사고·취약점 대응

- 사용자 영향, 데이터 노출, 배포 실패가 생기면 되돌리기나 차단으로 먼저 피해를 줄인다.
- 이어서 비난 없는 짧은 사후 기록을 남긴다. 내용은 무엇이 일어났는지, 영향, 조치, 근본원인, 재발 방지다.
- 같은 유형을 막는 회귀 테스트를 추가한다.
- 취약점은 우선순위를 정해 고치고 근본원인을 기록한다.

## DEV-14 기록·결정

- **기록 범위**: 일반 등급은 PR 본문과 STATUS.md에 남긴다. 고위험은 여기에 `ops/` 수락 기록을 더한다.
- 되돌리기 어려운 결정은 스펙의 "결정" 절에 맥락·결정·결과로 쓴다.
- 과거 영수증은 고치지 않는다. 후속 기록으로 바로잡는다.
- AI 실행 로그는 [AGENTS.md](../AGENTS.md) 규칙대로 남긴다. 일반 등급에서는 PR 하나를 "주요 단계" 하나로 본다.
- [CHANGELOG.md](../CHANGELOG.md)는 배포 단위로 한 줄씩 쓴다.
